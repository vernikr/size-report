# agent-audit — пригодность репозитория для ИИ-агентов

Переиспользуемый комплект аудита: насколько легко кодинг-агенту (уровня сентября 2026:
Codex, Claude Code, Cursor, Gemini CLI и т.п.) ориентироваться в репозитории и во что
ему обходится контекст. Применим к любому проекту на любом языке.

## Модель аудита: два слоя

1. **Статический** — `scan.sh`: детерминированные метрики по дереву и истории
   (объём входного контекста, масса-отвлекатели, целостность ссылок и команд,
   находимость, петля обратной связи). Запускается за секунды, без LLM,
   воспроизводим в CI.
2. **Поведенческий** — `probes/`: батарея зондов, которые выполняет живой агент
   в чистой сессии (ориентация, локализация правки по истории, проверка запретов,
   мелкая починка). Статика не видит поведение — зонды видят. Оценивается человеком
   по рубрикам; часть автоматизируется в headless-режиме.

Итог сводится в `scorecard.md`. Статика без зондов допустима, но помечается
«только статика» — она измеряет потенциал, а не результат.

## Почему так, а не иначе (кратко; источники — в `references.md`)

- **Окно контекста — бюджет внимания, а не свободное место.** Качество деградирует
  с длиной даже на релевантном тексте (Chroma «Context Rot», 18 моделей;
  «длина сама по себе вредит даже при идеальном поиске», арХив 10/2025).
  Эффективная длина окна в разы меньше заявленной (RULER, NoLiMa: 11 из 13 моделей
  ниже 50% базы уже на 32K). Отсюда — метрики массы и «мин».
- **Автозагружаемый контекст должен быть коротким и неочевидным.** Эмпирика
  ETH (арХив:2602.11988, 138 репо / 5694 PR): LLM-сгенерированные контекст-файлы
  вредят (−0.5…−2 п.п.), человеческие дают в среднем +4 п.п., оба типа дороже
  на 20–23% по инференсу и +14–22% по reasoning-токенам. Обзоры структуры файла
  не помогают навигации; помогают только сведения, которые агент сам не добудет.
  Контр-замер (JAWs 2026): короткий файл дал −28% времени и −20% выходных токенов —
  то есть файл влияет и на качество, и на эффективность, и мерить надо оба.
- **Неверная документация хуже отсутствия.** Некорректные доки −22.6 п.п. успеха
  (Macke & Doyle 2024); вводящие в заблуждение комментарии роняют локализацию
  дефектов до ~25% (Jia et al. 2025). Отсюда — метрики целостности ссылок/команд
  и свежести, самые весомые в скоринге.
- **Проверка собственных работ — наибольший рычаг.** Агенту нужны быстрые
  детерминированные тесты/линтеры/сборка (практика Claude Code, SWE-bench).
  Отсюда — метрики петли обратной связи.
- **Разведка — отдельная дорогая фаза.** Обзор затрат токенов (арХив:2604.22750):
  агентные задачи ~1000× дороже чата о коде, фазы Explore и Fix — самые дорогие,
  разброс затрат на одной задаче до 30×. Бенчмарки разведки (SWE-Explore
  арХив:2606.07297, IssueLoc-Bench арХив:2608.29675) показывают: качество
  разведки предсказывает успех починки, а дешёвый разведчик экономит 84–95%
  токенов. Отсюда — зонд локализации и метрики находимости.

## Запуск

```sh
bash agent-audit/scan.sh .          # статический слой, человекочитаемо + JSON
bash agent-audit/scan.sh . --json отчёт.json
```

Затем по желанию — `probes/` (00 подготовка → 01–04 зонды) и сборка `scorecard.md`.

## Каталог метрик (статика)

| Код | Метрика | Порог | Основание |
|---|---|---|---|
| A1 | Есть агентский контекст-файл (AGENTS.md и т.п.) | наличие | стандарт agents.md (60k+ репо, 30+ инструментов) |
| A2 | Токенов в автозагружаемых файлах | ≤2K / ≤4K / >4K | ETH: цена +20–23%; практика <200 строк |
| A3 | Токенов в README | ≤12K | эффект начала окна; прогрессивное раскрытие |
| A4 | Один канонический файл инструкций | без дублей-конкурентов | расползание = риск противоречий |
| B1 | Мёртвые пути/ссылки в документах | 0% / ≤3% / ≤10% | неверные доки −22.6 п.п. |
| B2 | Команды из документов сходятся с манифестом | 100% | «наличие ≠ проверенность» |
| C1 | Самый большой документ (токены) | ≤8K / ≤32K | мина в контексте; рот растёт с длиной |
| C2 | Суммарная масса корневых документов | ≤60K | отвлекатели усиливают деградацию |
| C3 | Число трекаемых файлов >10K токенов | 0 / ≤3 / ≤8 | карта репо должна влезать в бюджет |
| D1 | Уникальность имён файлов (без расширения) | ≥95% | неоднозначность ломает навигацию |
| D2 | Макс. число файлов в каталоге | ≤60 | стоимость разведки (SWE-Explore) |
| D3 | Токенов во всём коде | ≤200K / ≤600K | бюджет репо-карты (Aider) |
| E1 | Найден вход в тесты | наличие | проверяемость — главный рычаг |
| E2 | Есть CI | наличие | внешний проверяющий контур |
| E3 | Локфайл + пины версий | наличие | воспроизводимость среды агента |
| E4 | Хуки + дисциплина размера коммита (p75) | ≤1000 строк | маленькие коммиты = дешёвый `git log`-контекст |

Оценки токенов в скрипте — эвристика (±20%); для точных — установить
`gpt-tokenizer` в целевом репо, скрипт переключится сам. Пороги подобраны
консервативно: эвристика скорее завысит, и флаг всё равно полезен.

## Встраивание в рутину

- Локально: `bash agent-audit/scan.sh .` перед приёмом работы агентов над проектом
  и после крупных реорганизаций документации.
- CI (пример для GitHub Actions): шаг `bash agent-audit/scan.sh . --json out.json`
  и гейт на общий балл (например, падать при <55) или на регресс балла относительно
  предыдущего запуска (хранить как артефакт).
- Тренд: балл и флаги каждого запуска складывать в таблицу — аудит ценен динамикой,
  а не разовым снимком.

## Ограничения

- Эвристика токенов ±20%; флаги от этого не меняются по знаку, абсолютные числа —
  ориентир, а не бенчмарк.
- Статика не проверяет семантику документации (устаревшие советы при синтаксически
  живых ссылках) — это работа зондов и человека.
- Баллы сравнимы только между запусками одной версии скрипта.
