## 4. 2026-09-14 — починка B1: вывод больше не зависит от настроек git

4.1. **Запрос.** Закрыть B1 — единственный найденный дефект, который делал числа
тихо неверными на машинах с настройками git по умолчанию. Приёмка: паритет с
фикстурой и с живым проектом остаётся побайтово зелёным и при обычном глобальном
конфиге, и при `GIT_CONFIG_GLOBAL=/dev/null`; фикстура после починки даёт 14 строк
вместо 13; свидетель, утверждавший неправильное поведение, заменён утверждением
правильного. Чинить одним местом — на границе вызова git; другие настройки того же
класса — проверить, дешёвые закрыть здесь же, остальные — в план и блокеры.

4.2. **Что нашлось (проба, а не догадка).** Прогон движка в клоне фикстуры с
одной подсунутой настройкой и сравнением с эталоном побайтово:

| Настройка | Строк | Эталон |
|---|---|---|
| `core.quotePath=true` | 13 | **нет** |
| `core.autocrlf=true`, `core.eol=crlf` | 14 | да |
| `color.ui=always`, `log.showSignature=true` | 14 | да |
| `i18n.logOutputEncoding` и `i18n.commitEncoding` = ISO-8859-1 | 14 | да |
| `diff.renames=false`, `log.decorate=full`, `core.abbrev=4`, `log.date=relative` | 14 | да |
| `pager.log=true`, `GIT_PAGER=less`, `status.showUntrackedFiles=no` | 14 | да |
| `LC_ALL=C`, `LANG=C` | 14 | да |

Отдельно проверил: `diff.renames` на список путей не влияет вовсе —
`git show --name-only` отдаёт в коммите-переименовании оба пути при любом значении
настройки, то есть закреплять там нечего. И нашлась вторая, отдельная беда: в
согласованной выкладке с `core.autocrlf=true` (значение по умолчанию в установке
Git для Windows) инструмент падает с ложным «перенос состояния пропустил правку»:
735 Б в git против 749 Б на диске — это запись B2, она требует правки механики и
ушла отдельным пунктом.

4.3. **Сделано.** Настройки закреплены в одном месте (`src/size-table.js`, блок
«граница вызова git»): сборщик аргументов добавляет `--no-pager` и четыре
`-c`-настройки (`core.quotePath=false`, `color.ui=never`,
`log.showSignature=false`, `i18n.logOutputEncoding=UTF-8`), а окружение
подпроцессов получает `LC_ALL=C`, `LANG=C`. Пять вызовов git (корень репозитория,
общий запуск, чтение блобов пачкой, выдача содержимого, черновик конфига) сведены
к этому сборщику — шестой вызов в файле не git (`node --check` в гарде стриппера),
его не трогал. Механика не переписывалась: изменены только строки вызова.

Свидетель прежнего поведения заменён утверждением правильного: тест сверяет вывод
с эталоном в четырёх заведомо чужих окружениях и отдельно требует, чтобы в
окружении без настроек машины фикстура дала столько же строк, сколько в эталоне,
колонка с не-ASCII меткой была заполнена, а коммит строку получил.
`tools/parity-live.js` теперь сверяет две среды вместо одной.

`core.autocrlf=true` (в установке Git для Windows это значение по умолчанию)
инструмент отказывался работать и врал о причине. Приёмка из двух частей: (1) в этом
окружении прогон даёт те же числа и тот же sha256 артефакта, что в обычном;
(2) мутацией доказать, что сверка ещё что-то стережёт — правка файла только на диске
должна быть поймана. Ограничения: одна точка правки, без переделки механики; паритет
с фикстурой и живым проектом побайтово зелёный во всех средах.

6.2. **Что нашлось до правки (пробами, а не догадками).**

- Воспроизведение B2: клон `-c core.autocrlf=true` плюс `config core.autocrlf true`
  (согласованное окружение: `git status` пуст) — на диске `src/code.js` 749 Б против
  735 Б в git, прогон падает с ложным «перенос состояния … пропустил правку».
- Пункт D6 (сверять `hash-object` файла с хешем блоба) решает не всё: в фикстуре есть
  файл с CRLF внутри самого коммита (`notes/crlf.txt`), и при `core.autocrlf=true`
  выкладка оставляет его как есть, а «очистка» вернула бы LF — хеши не сходятся, и
  инструмент падает снова, теперь на этом файле. `git status` такие файлы считает
  чистыми (смотрит на запись о файле в индексе), сам git про них предупреждает.
- Отличить «файл, который git не возвращает обратно» от «правки на диске» хешем
  нельзя — нужен обратный перевод: `git cat-file --filters HEAD:<путь>` отдаёт то,
  что git сам выложил бы на диск. Пакетного `--filters` у git нет (проверено:
  `--batch --filters` фильтры молча игнорирует), поэтому это вызов на файл — он
  остаётся запасным путём: 35 мс на файл против 0,03 с на весь список у пакетного
  `hash-object --stdin-paths`.

6.3. **Сделано** (одна функция `assertMatchesDisk` плюс хеш блоба в состоянии):

- **Состояние против дерева коммита.** `git ls-tree -r -z HEAD` — правда о
  содержимом HEAD, добытая не тем же способом, что состояние. Колонка, у которой в
  состоянии файла нет, обязана быть пустой и в дереве (иначе потеряно создание
  файла). Один вызов на прогон.
- **Файл на диске против того же содержимого.** `git hash-object --stdin-paths` —
  один вызов на все файлы; если хеш не сошёлся, содержимое сверяется с
  `git cat-file --filters HEAD:<путь>`: совпало — это необратимая выкладка, а не
  правка.
- Файлы, изменённые в дереве, выпадают из сверки с диском, как и раньше.
- Сверка стала точнее: сравнение по содержимому ловит правку, не изменившую размер
  (раньше такая проходила мимо), и потерянное создание файла.

6.4. **Результат.**

| Прогон | Итог |
|---|---|
| `pnpm test` | 15 из 15, 14 с (было 12: три проверки — сверка с деревом) |
| Новые проверки на движке **до** починки (клон `d50ac42`) | красная «выкладка с CRLF не мешает сверке» (это и есть дефект) и красная «правка только на диске» (в CRLF-выкладке падало раньше, на другом файле) |
| Мутация «сверка с диском стала пустышкой: сравниваем дерево с деревом» | роняет ровно одну проверку: «правка файла только на диске ловится» |

6.5. **Заметки.**

- Проверка «зубов» сверки держится сценарием: файл помечается
  `--assume-unchanged`, и правка на диске остаётся невидимой для `git status` — это и
  есть «правка только на диске». Если бы правка попала в статус, файл считался бы
  грязным и из сверки выпал бы (так и задумано), и проверять было бы нечего; тест
  это утверждает отдельно.
- Мутация «потерянная правка merge-коммита» воспроизводит исторический дефект, ради
  которого сверка написана: из чтения истории убирается `--diff-merges=first-parent`,
  и правка разрешения конфликта выпадает из состояния. Мутируется **копия** движка
  во временном каталоге, а тест сначала утверждает, что мутация применилась: если
  код переустроят, проверка упадает с объяснением, а не промолчит.
