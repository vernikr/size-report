# Отчёт: механизм работы `size-report.html` и оптимизация отклика на чекбоксы

## 1. Как страница устроена и что происходит при клике

Артефакт — один самодостаточный файл на 1.44 MB (без сети и внешних ссылок): стили, блок данных `<script id="data">` (JSON на 1.37 MB), словарь подписей и программа, вклеенная из шести глав исходников (`derived.js` — общий расчёт, `state.js` — выбор и память, `dom.js` — узлы, `panel.js` — дерево, `table.js` — таблица, `app.js` — сборка).

Данные в этой сборке: 261 файл-колонка, 211 коммитов + строка «сейчас», 3 метрики (raw/min/tok), каталог из 274 путей. Значения хранятся построчно: для каждого коммита массив по всем 261 файлам из `{raw, min, tok}` или `null`.

Ключевой факт механики: **любой клик по любой галочке (файл, папка, категория, метрика) запускает один и тот же полный конвейер** — перестраивается вся панель с деревом файлов, затем вся таблица с нуля (сначала очистка узла таблицы, потом создание всех строк заново), затем запись выбора в память браузера и адрес. Обработчик клика меняет только флаг в состоянии выбора — вся остальная цена одинакова для всех трёх типов чекбоксов из вашего списка.

Числа перед каждым пересчётом считаются заново: для каждой строки коммита и каждой метрики суммируются включённые файлы, то же — для предыдущей строки (для дельт), затем каждая ячейка превращается в DOM-узел. Плюс карта приближённых клеток сканируется посимвольно для каждой клетки итога.

## 2. Замеры на живой странице (Chrome, эта сборка)

| Взаимодействие | Время | Что за ним стоит |
|---|---|---|
| Чекбокс метрики raw/min/tok | 0.5 – 3.0 с | полный rebuild: 166 632 ячеек |
| Чекбокс категории (Код/Документация/Служебные) | 0.6 – 2.3 с | то же |
| Чекбокс папки (docs/, 17 файлов) | 0.6 – 1.8 с | то же |
| Чекбокс одного файла | 0.7 – 2.2 с (выбросы до 8 с) | то же |
| Складывание папки (знак ▸/▾) | **0.4 мс** | класс на строке, без rebuild |
| Стартап до DOMContentLoaded | ~4.9 с | сборка 174 243 DOM-узлов |
| …из них только чтение JSON | 35 мс | не является узким местом |
| Только очистка таблицы (`textContent=''`) | ~0.5 с | разрушение 166k узлов |

Объёмы, объясняющие цифры: таблица — 212 строк × 787 ячеек ≈ **167k ячеек**, всего **174k DOM-узлов**; панель — 304 инпута и ~2k узлов (малая доля). Арифметика пересчёта — ~330k операций, это единицы-десятки **миллисекунд**: тормозит не счёт, а DOM.

Важные следствия:

- **Асимметрия «включить дороже выключить»** и плавающий разброс времён — мусор от предыдущего разрушения: GC чистит мёртвые узлы, и следующая сборка на замусоренной куче в разы дороже. Это лечится только отказом от teardown/rebuild.
- Складывание папки (0.4 мс) — доказательство потолка: точечное изменение без пересборки на два порядка быстрее, и именно оно показывает целевую планку для всех чекбоксов.
- Пересборка панели — отдельный гвоздь программы: она ломает прокрутку и фокус, которые затем вручную восстанавливаются, т.е. проблема создана самой пересборкой.

## 3. Корневые причины, по убыванию веса

1. **Полное разрушение и пересоздание таблицы на каждый клик** — создание узлов + раскладка/отрисовка гигантской таблицы + GC. ~95% цены клика.
2. **Пересборка панели целиком** — ~2k узлов, сброс scroll/focus и их восстановление.
3. **Избыточный пересчёт**: суммы по всем строкам заново при изменении одного файла; посимвольное сканирование карты приближений на каждую клетку итога; повторная стабильная сортировка колонок.
4. **Модель данных**: values — 55 071 объект-тройка, из которых лишь **1 159 уникальных**, плюс 24 740 null → 1.18 MB из 1.37 MB payload (87%). Парсинг быстрый (35 мс), но память, кэш и стартап платят за лишнее.
5. Запись выбора (stringify + localStorage + замена адреса) на каждый клик — мелочь, но зря.

## 4. Варианты оптимизации

### Ярус 1 — быстрые победы, без смены архитектуры

1. **Инкрементальные итоги через дельты.** Дельта файла по строке не зависит от выбора читателя, а итог линеен: дельта суммы = сумма дельт включённых (это гарантируется контрактом знаков). Значит, готовые дельты считаются один раз при старте, и клик стоит O(строки × метрики × включённые файлы) сложений — миллисекунды вместо полного пересчёта с двумя суммами на строку.
2. **Кэш содержимого клеток.** Содержимое клетки файла не зависит от других файлов — меняется лишь её видимость. Тексты клеток колонки считаются один раз (или лениво), клик переиспользует их. Итоги — п.1.
3. **Прединдексация карты приближений**: единицы собираются в массив позиций один раз — O(1) на клетку вместо посимвольного прохода.
4. **Панель точечно**: дерево строится один раз; клик файла обновляет `checked`/`indeterminate` только папок-предков (карта «файл → папки»), клик папки/категории — их инпуты. Scroll/focus перестают быть проблемой в принципе.
5. **Debounce записи** выбора в память и адрес (150–300 мс, пропуск при неизменившемся выборе).

### Ярус 2 — целевое решение: сетка строится один раз

6. **In-place вместо rebuild**: при первом построении создаётся супермножество сетки (все файлы × все метрики), дальше только скрытие/показ. Клик файла/папки/категории — скрыть/показать ~212 клеток его колонки (или один `<col>` с `visibility: collapse` — один стиль на колонку; понадобится проверка липкой шапки в браузерах, запасной путь — класс на клетках). Клик метрики — скрыть/показать один подстолбец каждой колонки. Физический порядок колонок фиксирован при первой сборке («колонки последнего коммита вперёд»), скрытие его не ломает — существующий тест это и требует. Итог: клик в десятки мс, нулевой мусор для GC.
7. **Сборка строк строками** (`innerHTML`/`insertAdjacentHTML` вместо узел-за-узлом) — стартап и любой полный рендер дешевле в 3–5 раз; потребуется экранирование подписей коммитов (сейчас их страхует `textContent`).

### Ярус 3 — формат данных и масштаб (разрешено менять всё)

8. **Словарное сжатие values**: 1 159 уникальных троек → таблица троек + ссылки-индексы в строках (или колоночное хранение по метрикам). Оценка: 1.37 MB → ~0.3 MB, стартап и память — в разы меньше. Цена: смена `schema` в данных, правка сборщика и контрактных тестов.
9. **Виртуализация строк**: в DOM держатся только видимые ~15–20 строк (распорки сверху/снизу, реакция на прокрутку). 174k узлов → ~15k: стартап ~0.3–0.5 с **независимо от длины истории**, отчёт перестаёт деградировать с ростом числа коммитов. Совместимо с липкой шапкой и колонкой коммита, но это самая крупная правка (`table.js`/`app.js` + немного CSS).
10. `content-visibility: auto` на строки — дешевле п.9, но для таблиц требует фиксированных ширин колонок (`table-layout: fixed`), иначе браузер не может пропустить раскладку корректно; колонка коммита ширину уже имеет. Годится как проба, если не взлетит — п.9.

### Что нельзя сломать (ограничения репозитория)

- **Один расчёт**: страница обязана считать теми же функциями общего расчёта (`rowModel`/`cellParts`), второго способа счёта тесты не позволят — инкрементальность реализовывать внутри него или поверх, переиспользуя узлы, а не пересчитывая по-своему.
- Самодостаточность файла с диска: без сети, без динамических импортов, вклейка построчная.
- Неподвижная точка артефакта и контрактные тесты данных: смена формата — только через версию схемы.
- Рекомендуемый порядок: п.1–5 (максимум эффекта на вложенный час), затем п.6 как целевое; п.8–9 — отдельными порциями, если отчёт будет расти по истории.

Складывание папки трогать не нужно — там уже сделано правильно, и это образец для остальных кликов.
