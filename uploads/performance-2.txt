# Анализ производительности `size-report.html`

## Краткий вывод

Текущая архитектура при любом изменении фильтров фактически выполняет полный рендер:

1. Полностью пересоздаётся панель фильтров.
2. Полностью пересоздаётся `<table>`.
3. Для каждой строки истории заново вычисляются:
   - totals;
   - delta относительно предыдущего коммита;
   - значения всех видимых файлов;
   - DOM-узлы всех ячеек.
4. Старый DOM удаляется через `textContent = ''`.
5. Новый DOM вставляется в документ.
6. Выполняется layout/paint большой таблицы.

Для маленьких отчётов это нормально. Для большого проекта с тысячами коммитов и десятками/сотнями файлов стоимость становится примерно такой:

\[
O(R \times F \times M)
\]

где:

- `R` — число строк истории;
- `F` — число файлов;
- `M` — число выбранных метрик.

Причём это происходит даже если изменение фильтра не требует пересчёта всей таблицы.

Главное узкое место находится в связке:

```js
appRender()
  -> appPanel()
  -> appTable()
    -> appBody()
      -> appRow()
        -> rowModel()
```

В `src/page/app.js`:

```js
function appRender(keepNotice) {
  ...
  appPanel();
  ...
  appTable();
}
```

В `src/page/table.js`:

```js
export function appBody(metrics, files) {
  const body = appEl('tbody');
  for (let r = appData.rows.length - 1; r >= 0; r--) {
    body.appendChild(appRow(r, metrics, files));
  }
  ...
}
```

А `appRow()` каждый раз вызывает `rowModel()`:

```js
const model = rowModel(
  row.values,
  prev === null ? null : prev.values,
  metrics,
  appView.files
);
```

При этом текущая модель данных уже содержит абсолютные значения, поэтому `rowModel()` повторно суммирует и повторно вычисляет delta при каждом клике.

# 1. Текущее поведение по типам взаимодействий

## 1.1. Клик по категориям файлов

Речь идёт о категориях:

- `Код`;
- `Документация`;
- `Служебные`;
- также потенциально `Ресурсы`.

Обработчик создаётся в `src/page/panel.js`:

```js
appData.categories.forEach((cat) => {
  const idx = [];
  appData.files.forEach((f, i) => {
    if (f.category === cat.key) idx.push(i);
  });

  cats.appendChild(appBox(
    cat.label,
    ...,
    idx.every((i) => appView.files[i]),
    (e) => {
      idx.forEach((i) => {
        appView.files[i] = e.target.checked;
      });
      appRender();
    },
    'all'
  ));
});
```

### Что происходит сейчас

1. Проход по всем файлам для поиска файлов категории.
2. Изменение `appView.files` для каждого файла категории.
3. Полное пересоздание панели.
4. Полное пересоздание таблицы.
5. Повторный расчёт всех строк истории.

### Важная особенность

Категория не имеет собственного состояния. Она лишь массово изменяет состояния файлов:

```js
idx.forEach((i) => {
  appView.files[i] = e.target.checked;
});
```

Это правильная модель с точки зрения консистентности, но поиск `idx` выполняется при каждом рендере. Его следует построить один раз.

### Стоимость

Если категория содержит `Fc` файлов:

- изменение состояния категории: `O(Fc)`;
- построение панели: `O(F + число_папок × размер_поддерева)`;
- построение таблицы: `O(R × F × M)`.

Доминирует последний пункт.

---

## 1.2. Клик по `raw`, `min`, `tok`

Обработчик также находится в `src/page/panel.js`:

```js
appData.metrics.forEach((m) => {
  ...
  mrow.appendChild(appBox(
    m.label,
    ...,
    appView.metrics[m.key],
    (e) => {
      appView.metrics[m.key] = e.target.checked;
      appRender();
    },
    'metric'
  ));
});
```

### Что происходит сейчас

При переключении метрики:

1. Меняется один флаг `appView.metrics[m.key]`.
2. Полностью перестраивается панель.
3. Полностью перестраивается таблица.
4. Для каждой строки вызывается `rowModel()`.
5. Все ячейки перерисовываются, хотя большинство файлов и строк не изменились.

### Почему это особенно неэффективно

При смене метрики структура таблицы меняется:

```text
commit | total raw | total min | file A raw | file A min | ...
```

Но можно было бы изменять только:

- заголовок;
- набор ячеек метрики;
- `colSpan`;
- классы видимости колонок.

Сейчас вместо этого уничтожается весь `<table>`.

### Дополнительная проблема

`rowModel()` рассчитывает все выбранные метрики заново:

```js
metrics.forEach((m) => {
  out[m] = 0;
});
```

Даже если были заранее рассчитаны значения для всех метрик, приложение снова суммирует их для каждой строки.

---

## 1.3. Клик по чекбоксу папки

Обработчик папки:

```js
function appDirHead(name, sub) {
  const idx = appIndexes(sub);
  ...
  head = appBox(..., (e) => {
    idx.forEach((i) => {
      appView.files[i] = e.target.checked;
    });
    appRender();
  }, 'dir');
}
```

### Что происходит сейчас

1. При построении дерева для каждой папки вызывается `appIndexes(sub)`.
2. `appIndexes()` рекурсивно собирает все индексы файлов под папкой.
3. При клике изменяются все файлы под папкой.
4. Выполняется полный рендер панели и таблицы.

### Скрытая проблема алгоритма дерева

В `appTreeList()` для каждой директории вызывается:

```js
appIndexes(node.dirs.get(name)).length > 0
```

А затем сама папка снова вызывает:

```js
const idx = appIndexes(sub);
```

Для вложенного дерева одни и те же поддеревья могут обходиться многократно. В худшем случае построение дерева может приближаться к квадратичной сложности относительно количества папок и файлов.

### Дополнительный эффект

Клик по папке меняет видимость колонок и totals, поэтому пересчёт данных действительно нужен. Но пересоздавать весь DOM не обязательно.

---

# 2. Основные источники потерь производительности

## 2.1. Полная перерисовка таблицы

Это главная проблема.

```js
table.textContent = '';
table.appendChild(appHead(...));
table.appendChild(appBody(...));
```

На каждом клике заново создаются:

- `<thead>`;
- все `<tr>`;
- все `<td>`;
- все ссылки;
- все подписи коммитов;
- все текстовые узлы;
- все tooltip-атрибуты.

Если в таблице 5 000 строк, 100 файлов и 3 метрики, число ячеек может быть порядка:

\[
5000 \times (1 + 101 \times 3) \approx 1.5 \text{ млн ячеек}
\]

Полный DOM такого размера практически неизбежно будет тормозить.

---

## 2.2. Повторный расчёт totals и delta

В `rowModel()` на каждой строке выполняются:

```js
const total = totalsOf(values, metrics, on);
const prevTotal = prev === null ? null : totalsOf(prev, metrics, on);
```

При переключении одного файла пересчитывается total по всем файлам для каждой строки.

Если пользователь выключил один файл, текущая реализация всё равно:

- проходит по всем строкам;
- проходит по всем файлам;
- проверяет `on[i]`;
- суммирует остальные файлы.

---

## 2.3. Пересоздание панели

Даже при изменении одного metric checkbox заново создаются:

- все metric checkbox;
- все category checkbox;
- всё дерево файлов;
- все folder checkbox;
- все tooltips.

Панель обычно гораздо меньше таблицы, поэтому это не главный bottleneck, но это лишняя работа.

---

## 2.4. Нет виртуализации строк

Все строки истории сразу добавляются в DOM:

```js
for (let r = appData.rows.length - 1; r >= 0; r--) {
  body.appendChild(appRow(r, metrics, files));
}
```

Для длинной истории это дорого по:

- памяти;
- созданию DOM;
- layout;
- поиску стилей;
- прокрутке;
- garbage collection.

---

## 2.5. Не используется кэш вычислений

Исходные данные не меняются во время жизни страницы, меняется только выбор:

- набор metrics;
- набор files.

Поэтому множество значений можно вычислить один раз при загрузке:

- absolute values;
- per-file delta;
- per-file totals;
- approximate marks;
- category indexes;
- folder indexes;
- порядок колонок.

Сейчас значительная часть этих данных вычисляется повторно при каждом взаимодействии.

---

# 3. Варианты оптимизации

## Вариант A — минимально рискованный

Подходит, если требуется сохранить текущую архитектуру и HTML-формат.

### A1. Предрасчитать индексы категорий

Вместо:

```js
appData.files.forEach(...)
```

при каждом построении панели создать один раз:

```js
const filesByCategory = Object.create(null);

appData.files.forEach((file, index) => {
  const key = file.category;
  if (!filesByCategory[key]) filesByCategory[key] = [];
  filesByCategory[key].push(index);
});
```

Это ускорит создание category controls и сделает обработчик независимым от повторного поиска.

---

### A2. Предрасчитать индексы папок

Сейчас `appIndexes(sub)` вызывается неоднократно.

Лучше построить один индекс:

```js
const folderFiles = new Map();

function addFileToFolders(path, index) {
  const parts = path.split('/');
  let prefix = '';

  for (let i = 0; i < parts.length - 1; i++) {
    prefix = prefix ? prefix + '/' + parts[i] : parts[i];

    if (!folderFiles.has(prefix)) {
      folderFiles.set(prefix, []);
    }

    folderFiles.get(prefix).push(index);
  }
}
```

Тогда обработчик папки будет брать готовый массив:

```js
const idx = folderFiles.get(path) || [];
```

---

### A3. Перейти с `forEach` на обычные циклы в горячих местах

В коде построения таблицы вызывается множество callback-функций:

```js
metrics.forEach(...)
files.forEach(...)
values.forEach(...)
```

Для миллионов операций это заметно. В горячих циклах можно использовать обычные `for`:

```js
for (let i = 0; i < values.length; i++) {
  ...
}
```

Эффект будет умеренным, но изменение дешёвое и безопасное.

---

### A4. Использовать `DocumentFragment`

Сейчас строки добавляются по одной:

```js
for (...) {
  body.appendChild(appRow(...));
}
```

Лучше:

```js
const fragment = document.createDocumentFragment();

for (...) {
  fragment.appendChild(appRow(...));
}

body.appendChild(fragment);
```

Это уменьшит количество промежуточных вставок в DOM. Однако это не решает проблему создания всех элементов.

---

### A5. Разделить рендер панели и таблицы

Сейчас `appRender()` всегда вызывает оба рендера:

```js
appPanel();
appTable();
```

Следует сделать:

```js
function renderPanel() { ... }
function renderTable() { ... }

function onMetricChange() {
  renderMetricControls();
  renderTable();
}

function onFileChange() {
  renderFileControls();
  renderTable();
}

function onFolderFold() {
  updateOnlyFolderVisibility();
}
```

Для клика по folder checkbox таблица нужна, но для клика по знаку раскрытия/сворачивания — нет. Текущий код уже не пересоздаёт таблицу для fold sign, что хорошо; это поведение стоит сохранить.

---

## Вариант B — кэш вычислений и частичный рендер

Это наиболее рациональный вариант для текущей архитектуры.

## B1. Один раз рассчитать данные по каждой строке

При загрузке страницы построить структуру:

```js
const cache = {
  rows: [],
  now: [],
  totals: {
    raw: [],
    min: [],
    tok: []
  },
  deltas: {
    raw: [],
    min: [],
    tok: []
  }
};
```

Для каждого commit row:

```js
cache.rows[r] = {
  files: [
    {
      raw: ...,
      min: ...,
      tok: ...,
      rawDelta: ...,
      minDelta: ...,
      tokDelta: ...
    }
  ],
  total: {
    raw: ...,
    min: ...,
    tok: ...
  }
};
```

Но totals зависят от выбранных файлов. Поэтому желательно хранить не только итог, а prefix/sparse-структуру или возможность быстро пересчитать:

```js
total[metric][row][file]
```

---

## B2. Разделить значения файла и totals

Значения отдельного файла не зависят от фильтра файлов. Их надо считать один раз.

Для каждой строки:

```js
fileValues[row][file][metric]
fileDeltas[row][file][metric]
```

При переключении метрики:

- значения файлов не пересчитываются;
- меняется только количество отображаемых колонок.

При переключении файла:

- file columns можно показать/скрыть;
- totals пересчитать только для изменённого набора.

---

## B3. Быстрый пересчёт totals через суммы

Для каждого выбранного metric можно поддерживать текущую сумму на строку:

```js
currentTotals[metric][row]
```

При включении/выключении файла `f`:

```js
const sign = enabled ? 1 : -1;

for (let row = 0; row < rowCount; row++) {
  currentTotals[metric][row] += sign * fileValues[row][f][metric];
}
```

Стоимость переключения одного файла:

\[
O(R \times M)
\]

вместо:

\[
O(R \times F \times M)
\]

Это особенно эффективно для чекбоксов папок и категорий. Для папки с `K` файлами:

\[
O(R \times K \times M)
\]

вместо полного пересчёта всех `F` файлов.

---

## B4. Инкрементально обновлять DOM

Вместо полного рендера таблицы:

- при изменении metric — добавлять/удалять только соответствующие колонки;
- при изменении file — менять `hidden` у группы колонок;
- total columns обновлять текстом;
- не трогать commit captions.

Возможная структура DOM:

```html
<table>
  <thead>...</thead>
  <tbody>
    <tr data-row="0">
      <th class="commit">...</th>
      <td data-file="total" data-metric="raw"></td>
      <td data-file="0" data-metric="raw"></td>
      <td data-file="0" data-metric="min"></td>
    </tr>
  </tbody>
</table>
```

Тогда переключение файла:

```js
document.querySelectorAll('[data-file="17"]')
  .forEach((cell) => {
    cell.hidden = !enabled;
  });
```

Для больших объёмов лучше не использовать `querySelectorAll` на каждый клик, а хранить ссылки:

```js
cellsByFile[fileIndex] = [...];
```

---

## B5. Использовать CSS visibility вместо удаления DOM

Если максимальный набор колонок создаётся один раз, фильтры могут переключать CSS-класс:

```css
.col-hidden {
  display: none;
}
```

или:

```js
cell.classList.toggle('col-hidden', !enabled);
```

Преимущества:

- не требуется пересоздание элементов;
- сохраняются tooltip, ссылки и focus;
- меньше garbage collection;
- переключение UI становится почти мгновенным.

Недостаток: DOM максимального отчёта остаётся большим. Для отчётов на сотни тысяч ячеек это всё равно будет дорого.

---

# 4. Вариант C — виртуализация таблицы

Это наиболее эффективный вариант при большой истории.

## Идея

В DOM находятся только видимые строки плюс небольшой buffer:

```text
видимые строки: 100–300
buffer сверху: 50
buffer снизу: 50
```

Остальные строки представлены пустым spacer-элементом:

```html
<tbody>
  <tr class="spacer-top"></tr>
  <!-- 150 реальных строк -->
  <tr class="spacer-bottom"></tr>
</tbody>
```

При прокрутке:

1. определить диапазон видимых строк;
2. обновить только эти строки;
3. изменить высоту spacer-элементов;
4. сохранить общую высоту таблицы.

### Оценка

Вместо:

\[
O(R \times F \times M)
\]

на каждый render получается примерно:

\[
O(V \times F \times M)
\]

где `V` — число видимых строк, обычно 50–300.

Это может дать наибольший прирост.

## Ограничения

Виртуализация сложнее из-за:

- переменной высоты commit rows;
- горизонтальной прокрутки;
- сохранения ссылок;
- accessibility;
- поиска по браузеру;
- копирования таблицы;
- печати;
- ссылок на конкретные строки.

Можно начать с фиксированной высоты строки. Если высота строк стабильна, реализация существенно упрощается.

---

# 5. Вариант D — изменение модели исходных данных

Текущая модель хранит строки примерно как:

```js
rows: [
  {
    values: [
      { raw, min, tok },
      { raw, min, tok },
      ...
    ]
  }
]
```

Это удобно, но недостаточно оптимально для интерактивного фильтра.

## D1. Колонночная модель

Вместо массива объектов использовать typed arrays:

```js
{
  raw: Float64Array,
  min: Float64Array,
  tok: Float64Array,
  exists: Uint8Array
}
```

Индексация:

```text
offset = rowIndex * fileCount + fileIndex
```

Пример:

```js
raw[offset]
min[offset]
tok[offset]
```

### Преимущества

- меньше памяти;
- лучше cache locality;
- быстрее массовое суммирование;
- быстрее передача в Worker;
- меньше overhead JavaScript objects.

### Недостатки

- сложнее сериализация;
- сложнее читаемость;
- нужно отдельно хранить `null`/отсутствующие файлы;
- потребуется версия формата.

---

## D2. Хранить дельты заранее

Сейчас delta вычисляется во время отображения:

```js
deltaOf(value, was)
```

Можно сохранить:

```js
{
  values: ...,
  deltas: ...
}
```

Особенно это полезно для `raw`, `min`, `tok`, потому что эти значения не меняются в браузере.

Тогда `rowModel()` вообще не понадобится на пользовательском пути.

---

## D3. Хранить заранее агрегаты по категориям и папкам

В build-time можно сгенерировать:

```js
categoryFiles: {
  code: Uint32Array(...),
  docs: Uint32Array(...),
  chore: Uint32Array(...)
},

folderFiles: {
  "src": Uint32Array(...),
  "src/page": Uint32Array(...)
}
```

Это ускорит:

- клик по категории;
- клик по папке;
- вычисление состояния `all/some/none`.

---

## D4. Сохранять предварительно рассчитанные column groups

Можно сразу подготовить порядок колонок:

```js
columns: [
  { type: 'total', metric: 'raw' },
  { type: 'total', metric: 'min' },
  { file: 0, metric: 'raw' },
  { file: 0, metric: 'min' }
]
```

При переключении metric или file браузер не должен заново вычислять структуру таблицы.

---

# 6. Вариант E — Web Worker

Если отчёт очень большой, можно вынести вычисления в Worker.

## Что выносить

- расчёт totals;
- расчёт delta;
- построение видимого диапазона строк;
- подготовку текстовых значений;
- вычисление состояний folder/category checkbox.

Основной поток занимается:

- DOM;
- событиями;
- прокруткой;
- отрисовкой.

Пример протокола:

```js
worker.postMessage({
  type: 'set-files',
  enabledFiles
});
```

Worker отвечает:

```js
worker.postMessage({
  type: 'patch',
  rows: [
    {
      index: 120,
      total: {
        raw: '12 345',
        min: '9 876'
      },
      cells: [...]
    }
  ]
});
```

## Когда Worker оправдан

- история от нескольких тысяч строк;
- десятки или сотни файлов;
- есть задержки больше 50–100 мс;
- используется виртуализация.

Для маленьких отчётов Worker только усложнит код.

# 7. Рекомендации отдельно по каждому взаимодействию

## 7.1. Категория файла

### Сейчас

Стоимость:

```text
изменить K файлов
+ полностью построить панель
+ полностью пересчитать таблицу
+ полностью пересоздать DOM
```

### Рекомендуемый путь

1. Один раз построить `filesByCategory`.
2. Переключить состояния `K` файлов.
3. Инкрементально обновить totals:
   - вычесть/прибавить значения файлов категории;
4. Скрыть/показать колонки категории через CSS class;
5. Обновить только total cells;
6. Обновить состояние folder/category controls.

Целевая стоимость:

\[
O(R \times K \times M + R \times M)
\]

При виртуализации:

\[
O(R \times K \times M + V \times F \times M)
\]

---

## 7.2. Метрика `raw`, `min`, `tok`

### Сейчас

Полностью пересоздаются все строки и ячейки.

### Рекомендуемый путь

1. Каждый metric получает собственный column group.
2. У каждой колонки есть CSS-класс:
   - `.metric-raw`;
   - `.metric-min`;
   - `.metric-tok`.
3. При изменении checkbox:

```js
document.querySelectorAll('.metric-tok')
  .forEach((cell) => {
    cell.hidden = !enabled;
  });
```

4. Для totals не нужно пересчитывать данные — они уже рассчитаны или поддерживаются в cache.
5. Обновить только заголовки и `colSpan`.

Целевая стоимость при готовом DOM:

\[
O(\text{число ячеек выбранной метрики})
\]

Ещё лучше — использовать заранее сохранённые массивы ссылок на DOM-узлы.

---

## 7.3. Папка

### Сейчас

1. Рекурсивно собираются индексы файлов папки.
2. Меняются состояния всех файлов.
3. Полностью перерисовывается всё.

### Рекомендуемый путь

1. Заранее построить `folderFiles[path]`.
2. Изменить только файлы папки.
3. Инкрементально обновить aggregates.
4. Скрыть/показать соответствующие колонки.
5. Обновить состояние checkbox родителей.

Для вложенных папок полезно хранить:

```js
folderFiles[path] = Uint32Array(...)
folderParents[path] = [...]
```

Это позволит быстро пересчитать состояния родителей после изменения дочерней папки.

# 8. Что я бы выбрал

## Оптимальный план по этапам

### Этап 1. Низкий риск

Сделать без изменения формата отчёта:

1. Индексировать категории.
2. Индексировать папки.
3. Предрасчитать `fileValues` и `fileDeltas`.
4. Использовать `DocumentFragment`.
5. Разделить `renderPanel()` и `renderTable()`.
6. Не пересоздавать панель при каждом изменении таблицы.
7. Кэшировать состояние отображаемых колонок.

Ожидаемый эффект: примерно `2–5x` на средних отчётах.

---

### Этап 2. Частичный рендер

1. Создавать таблицу один раз.
2. Хранить ссылки на DOM-ячеки.
3. Переключать видимость колонок через CSS.
4. Обновлять totals только для затронутых файлов.
5. Не пересоздавать строки при смене metric/file.

Ожидаемый эффект: `5–20x` для повторных кликов, особенно при смене `raw/min/tok`.

---

### Этап 3. Виртуализация

1. Рендерить только видимые строки.
2. Добавить scroll-driven row window.
3. Хранить данные в колонночном формате.
4. При необходимости вынести вычисления в Worker.

Это решение для действительно больших отчётов.

# 9. Предлагаемая новая архитектура

```text
data
 ├─ files
 ├─ metrics
 ├─ rows
 ├─ indexes
 │   ├─ filesByCategory
 │   ├─ filesByFolder
 │   └─ parentFolders
 ├─ values
 │   ├─ raw
 │   ├─ min
 │   └─ tok
 ├─ deltas
 │   ├─ raw
 │   ├─ min
 │   └─ tok
 └─ approx

viewState
 ├─ enabledMetrics
 ├─ enabledFiles
 └─ foldedFolders

runtime
 ├─ currentTotals
 ├─ columnElements
 ├─ rowElements
 └─ visibleRowRange
```

Поток клика:

```text
click category/folder
  -> update enabledFiles
  -> update currentTotals incrementally
  -> update checkbox states
  -> toggle column visibility
  -> update total cells
```

```text
click metric
  -> update enabledMetrics
  -> toggle metric column groups
  -> update header colSpan
```

```text
scroll
  -> calculate visible row range
  -> render only visible rows
```

# 10. Итоговая оценка приоритетов

| Оптимизация | Сложность | Эффект | Приоритет |
|---|---:|---:|---:|
| Кэш индексов категорий | Низкая | Небольшой | Средний |
| Кэш индексов папок | Низкая | Средний | Высокий |
| `DocumentFragment` | Низкая | Небольшой | Средний |
| Кэш значений и delta | Средняя | Высокий | Очень высокий |
| Инкрементальные totals | Средняя | Очень высокий | Очень высокий |
| Разделение panel/table render | Низкая | Средний | Высокий |
| CSS-скрытие колонок | Средняя | Высокий | Высокий |
| Частичный DOM-рендер | Средняя | Очень высокий | Очень высокий |
| Колонночный формат данных | Высокая | Высокий | Средний |
| Virtual scrolling | Высокая | Максимальный | Для больших отчётов |
| Web Worker | Средняя/высокая | Высокий | После виртуализации |

Главный вывод: **первая и наиболее выгодная оптимизация — отказаться от полного пересоздания таблицы на каждый клик**. Для `raw/min/tok` достаточно переключать группы колонок. Для категорий и папок нужно поддерживать инкрементальные totals. Если отчёт может содержать тысячи строк, это следует дополнить виртуализацией строк.
