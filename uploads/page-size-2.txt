Ниже — варианты уменьшения физического размера `size-report.html` с сохранением быстрой работы чекбоксов.

## Что сейчас занимает место

`docs/size-report.html` имеет размер примерно **1,4 МБ**.

Страница состоит из:

1. HTML/CSS.
2. Встроенного JSON-блока `#data`.
3. Встроенного JSON-блока `#ui`.
4. Полного JavaScript-приложения.
5. Большого количества комментариев исходного кода, потому что `pageScript()` фактически вставляет исходники модулей в HTML:

```js
export function pageScript() {
  return pageSource('../derived.js') + '\n'
    + PAGE_PARTS.map((part) => pageSource(part)).join('');
}
```

`pageSource()` читает исходный файл как текст. Удаляются только `import` и `export`, но комментарии, пробелы и имена переменных остаются.

Это важное наблюдение: **самый дешёвый способ уменьшить файл — минифицировать встроенный JavaScript и CSS, не меняя модель данных**.

# 1. Вариант с наилучшим соотношением эффекта и риска: минификация встроенного JS/CSS

## Что делать

Перед вставкой в HTML:

- удалять комментарии;
- удалять лишние пробелы;
- сокращать безопасные конструкции;
- минифицировать CSS;
- по возможности сокращать локальные имена переменных.

Например, вместо текущего:

```js
/* The table's body: the commit rows built from the newest down... */
export function appBody(metrics, files) {
  const body = appEl('tbody');
  ...
}
```

в страницу попадало бы компактное представление:

```js
function appBody(e,t){const n=appEl("tbody");...}
```

## Влияние на клики

Если минификатор не меняет алгоритм, влияние будет практически нулевым:

- тот же DOM;
- те же функции;
- та же модель данных;
- те же события;
- меньше JavaScript, который нужно скачать/прочитать/распарсить.

Для этого варианта я бы не использовал агрессивное переписывание логики на первом этапе. Достаточно:

1. удалить комментарии;
2. сжать whitespace;
3. минифицировать CSS;
4. оставить структуру функций и данные без изменений.

## Ожидаемый результат

Обычно можно ожидать:

- JavaScript: уменьшение примерно в `2–5 раз`;
- CSS: уменьшение примерно в `2–4 раза`;
- общий файл: уменьшение на десятки или сотни килобайт.

С учётом того, что комментарии проекта очень подробные, эффект может быть особенно заметным.

## Важная совместимость

Текущий `pageScript()` удаляет модули построчно:

```js
.filter((line) => !/^import\s.*;\s*$/.test(line))
.map((line) => line.replace(/^export\s+(function|const|let|var|class)\s/, '$1 '))
```

Поэтому минификацию нельзя выполнять до этого шага обычным образом: после минификации `import` и `export` могут оказаться не на отдельных строках.

Правильная последовательность:

```text
исходники
  -> stripModules()
  -> минификация standalone JavaScript
  -> вставка в HTML
```

Либо нужно изменить сборщик так, чтобы минификатор работал с уже объединённым скриптом.

# 2. Не включать комментарии исходников в production-страницу

Сейчас HTML содержит практически весь документирующий текст из:

- `src/derived.js`;
- `src/page/state.js`;
- `src/page/dom.js`;
- `src/page/panel.js`;
- `src/page/table.js`;
- `src/page/app.js`.

Эти комментарии полезны для разработки, но пользователю они не нужны.

Можно добавить режим:

```js
pageScript({ minify: true })
```

или разделить:

```js
pageScript({ development: false })
```

В production:

- комментарии удаляются;
- сохраняются только необходимые лицензии;
- диагностические тексты остаются в `ui`, если они отображаются пользователю.

Это наиболее безопасная оптимизация, поскольку она вообще не меняет поведение приложения.

# 3. Сокращение имён ключей JSON

Сейчас данные, вероятно, содержат достаточно многословные ключи:

```json
{
  "metrics": ["raw", "min", "tok"],
  "files": [
    {
      "path": "src/page/app.js",
      "label": "app.js",
      "category": "code"
    }
  ],
  "rows": [
    {
      "values": [
        {
          "raw": 1234,
          "min": 900,
          "tok": 320
        }
      ]
    }
  ]
}
```

Для отчёта на несколько тысяч строк ключи объектов повторяются огромное количество раз. Это может занимать значительную долю файла.

## Более компактная форма

Например:

```json
{
  "m": ["raw", "min", "tok"],
  "f": [
    ["src/page/app.js", "app.js", 0]
  ],
  "r": [
    [1234, 900, 320]
  ]
}
```

Где:

```text
m = metrics
f = files
r = rows
0 = category code
```

Ещё компактнее — строки истории могут хранить только массивы:

```json
{
  "r": [
    [1234, 900, 320, 80, 70, 20]
  ]
}
```

А JavaScript знает, что каждые `M` значений относятся к одному файлу.

## Влияние на производительность

Если использовать обычные массивы и один раз нормализовать их при загрузке:

```js
const files = data.f;
const rows = data.r;
```

то влияние на клики будет небольшим.

Но не следует при каждом клике преобразовывать компактный JSON. Нормализацию надо выполнить один раз:

```js
const runtimeData = decodeData(compactData);
```

После этого фильтры работают с runtime-представлением.

## Рекомендуемая схема

Хранить в HTML компактные данные:

```js
const encoded = ...;
const appData = decodeData(encoded);
```

В памяти можно получить привычную структуру:

```js
{
  metrics: [...],
  files: [...],
  rows: [...]
}
```

Физический размер уменьшается, а код интерактивности почти не меняется.

---

# 4. Убрать повторяющиеся названия метрик из каждой строки

Для каждой строки и каждого файла сейчас, вероятно, используются объекты вида:

```json
{
  "raw": 1000,
  "min": 800,
  "tok": 250
}
```

Ключи `raw`, `min`, `tok` повторяются в каждом объекте.

Лучше хранить значения в фиксированном порядке:

```json
[1000, 800, 250]
```

Порядок задаётся один раз:

```json
{
  "metrics": ["raw", "min", "tok"]
}
```

В коде:

```js
const RAW = 0;
const MIN = 1;
const TOK = 2;
```

В памяти:

```js
value[fileOffset + RAW]
value[fileOffset + MIN]
value[fileOffset + TOK]
```

## Эффект

Это уменьшает:

- размер ключей;
- количество JSON-объектов;
- стоимость `JSON.parse`;
- размер heap после парсинга.

Это одна из наиболее полезных оптимизаций для большого количества строк.

---

# 5. Колонночная модель вместо объектной

Для текущих интерактивных действий удобна модель:

```text
rows[row][file][metric]
```

Но для физического размера выгоднее хранить данные колонками:

```json
{
  "raw": [...],
  "min": [...],
  "tok": [...]
}
```

Индекс:

```js
offset = rowIndex * fileCount + fileIndex;
```

Пример:

```js
raw[offset]
min[offset]
tok[offset]
```

## Ещё лучше — TypedArray после загрузки

В HTML можно хранить компактные массивы, а в памяти использовать:

```js
new Int32Array(...)
```

Преимущества:

- меньше памяти;
- быстрее последовательный перебор;
- удобнее инкрементально обновлять totals;
- меньше overhead на объекты.

Недостаток: полноценный JSON не умеет компактно представлять `Int32Array`. Поэтому можно:

1. хранить обычные массивы;
2. после загрузки конвертировать их в typed arrays.

Для действительно большой страницы можно хранить данные в base64 или бинарном формате, но это усложняет проект.

# 6. Отдельно кодировать повторяющиеся пути и подписи

Пути файлов и подписи коммитов могут занимать много места.

## 6.1. Словарь файлов

Вместо повторения имени в разных структурах:

```json
{
  "path": "src/page/app.js",
  "label": "app.js",
  "category": "code"
}
```

можно оставить только:

```json
["src/page/app.js", "app.js", 0]
```

Или, если `label` однозначно получается из пути:

```js
label = path.slice(path.lastIndexOf('/') + 1)
```

Тогда `label` вообще не нужно хранить.

Нужно сохранить `label` отдельно только если в текущей модели он отличается от basename.

---

## 6.2. Словарь повторяющихся строк коммитов

Если в истории есть повторяющиеся:

- даты;
- секции;
- имена веток;
- ссылки;
- типовые subject;

можно вынести их в словари:

```json
{
  "subjects": [
    "fix parser",
    "update docs"
  ],
  "rows": [
    [170, 0, 1, ...],
    [171, 1, 0, ...]
  ]
}
```

Но здесь экономия обычно ниже, чем от сокращения числовой модели.

---

## 6.3. Общий префикс путей

Для большого проекта можно хранить:

```json
{
  "prefixes": ["src/", "src/page/"],
  "files": [
    [1, "app.js"],
    [1, "table.js"]
  ]
}
```

Однако эта оптимизация усложняет tree-index и работу с путями. Я бы применял её только после измерения.

---

# 7. Дельты не обязательно хранить в JSON

В текущем коде delta вычисляется из абсолютных значений:

```js
deltaOf(value, before)
```

Если в JSON отдельно сохраняются и абсолютные значения, и deltas, данные дублируются.

Для физического размера лучше:

- хранить только абсолютные значения;
- вычислять delta один раз после загрузки;
- либо вычислять delta только для отображаемого диапазона строк.

Если текущая таблица содержит очень много commit rows, можно хранить только абсолютные values и lazy-кэш:

```js
const deltaCache = new Map();

function getDelta(row, file, metric) {
  ...
}
```

Но если клики приводят к полному рендеру таблицы, lazy-кэш не спасёт от повторного рендера. Он становится особенно эффективным вместе с виртуализацией строк.

# 8. Не дублировать `approx`-информацию строками

В `appApprox()` используется строка битов:

```js
const marks = appData.approx[key];
```

И затем:

```js
row.charAt(base + files[i]) === '1'
```

Это уже достаточно компактная модель по сравнению с массивом boolean, но её можно сделать ещё компактнее.

## Вариант 1: битовая упаковка

Вместо строки:

```text
001001010001...
```

хранить байтовую строку или base64.

Один байт содержит 8 флагов:

```js
byte = bits[index >> 3];
isApprox = (byte & (1 << (index & 7))) !== 0;
```

Это уменьшает размер примерно в 8 раз относительно текстовой строки битов.

## Вариант 2: хранить только исключения

Если approximate cells редки:

```json
{
  "approx": {
    "tok": [12, 49, 51, 1003]
  }
}
```

Если approximate cells частые, bitmap будет лучше.

---

# 9. Использовать JSON без форматирования

В `pageHtml()` уже используется:

```js
JSON.stringify(value)
```

Это хорошо: JSON не форматируется с indentation.

Но дополнительно следует:

- не хранить неиспользуемые поля;
- удалять debug-поля до сериализации;
- не хранить UI-тексты, которые не используются;
- не хранить `skipped`, если он уже удаляется через `pagePayload()`.

Стоит проверить все поля `data`, потому что физический размер часто увеличивается не только от `rows`, но и от дублирующихся служебных структур.

---

# 10. Сжать числовые значения

Если размеры гарантированно не превышают диапазон `0..2^32-1`, можно использовать unsigned 32-bit представление.

В JSON обычные числа уже не имеют отдельного типа, но можно использовать дельта-кодирование.

## Дельта-кодирование по истории

Если размеры между соседними commit rows меняются незначительно:

```text
1000, 1012, 1015, 1014
```

можно хранить:

```text
1000, +12, +3, -1
```

После загрузки восстановить:

```js
value[i] = value[i - 1] + delta[i];
```

Для JSON это полезно в сочетании с более компактным integer-кодированием.

## Varint/base64

Для максимального уменьшения можно кодировать числа как varint:

```text
[1000, 12, 3, 1] -> base64
```

Плюсы:

- существенно меньший файл;
- быстрый последовательный decode;
- удобен для TypedArray-представления.

Минусы:

- собственный бинарный формат;
- сложнее отладка;
- надо тестировать совместимость;
- нельзя просто открыть JSON и посмотреть данные.

Я бы рассматривал varint только для крупных отчётов, где обычный компактный JSON уже недостаточен.

---

# 11. Brotli/gzip — важное ограничение

Можно упаковать HTML в `.html.gz` или `.html.br`, но это не уменьшит размер самого файла `size-report.html` на диске. Это поможет только если:

- файл отдаётся веб-сервером;
- сервер поддерживает `Content-Encoding`;
- пользователь не открывает HTML напрямую с диска.

Так как проект специально делает self-contained страницу, которая открывается двойным кликом, gzip/Brotli нельзя считать заменой оптимизации формата.

Можно хранить дополнительно:

```text
size-report.html
size-report.html.br
```

Но основной физический HTML останется прежним.

# 12. Что не стоит делать

## 12.1. Не удалять данные, необходимые для фильтров

Нельзя оставлять только текущие totals, если пользователь должен фильтровать файлы. Для пересчёта totals нужны значения каждого файла.

Минимально необходимы:

```text
row × file × metric
```

или эквивалентная модель.

---

## 12.2. Не хранить только готовую HTML-таблицу

Готовый HTML может быть быстрее при первом отображении, но:

- физический размер будет больше;
- фильтры будут требовать дублирования таблиц;
- сложно обновлять totals;
- HTML содержит много повторяющейся разметки.

Для интерактивной страницы лучше хранить данные и строить DOM.

---

## 12.3. Не использовать чрезмерное base64-кодирование без декодера

Base64 увеличивает бинарные данные примерно на 33%. Он выгоден только вместе с:

- бинарной упаковкой;
- varint;
- TypedArray;
- хорошим decode-кодом.

Если просто закодировать обычный JSON в base64, файл станет больше.

---

# 13. Рекомендуемый компромисс

Я бы выбрал следующую комбинацию.

## Шаг 1. Production-минификация

Уменьшить:

- встроенный JavaScript;
- CSS;
- удалить комментарии;
- удалить лишние пробелы.

Это не меняет runtime-модель и почти не влияет на клики.

## Шаг 2. Компактный JSON-массив

Заменить объекты значений:

```json
{"raw":1000,"min":800,"tok":300}
```

на:

```json
[1000,800,300]
```

Метрики объявить один раз:

```json
["raw","min","tok"]
```

## Шаг 3. Убрать дублирующиеся поля

Проверить возможность удалить или вычислять:

- `label` из `path`;
- повторяющиеся category descriptions;
- повторяющиеся metric keys;
- лишние runtime/debug-поля;
- повторяющиеся paths;
- уже неиспользуемые поля.

## Шаг 4. Упаковать approximate flags

Заменить строку битов на bitmap, если это даст измеримый выигрыш.

## Шаг 5. При необходимости — varint для чисел

Применять только если после первых четырёх шагов файл всё ещё слишком велик.

# 14. Приблизительная оценка вариантов

| Подход | Уменьшение файла | Влияние на клики | Сложность |
|---|---:|---:|---:|
| Удаление комментариев | Среднее/высокое | Нет | Низкая |
| Минификация JS/CSS | Среднее | Нет или небольшой плюс | Низкая |
| Компактные ключи JSON | Среднее | Нет после decode | Низкая |
| Массивы вместо объектов metrics | Высокое для больших данных | Нет/плюс | Средняя |
| Удаление дублирующихся labels | Небольшое/среднее | Нет | Низкая |
| Bitmap для approx | Небольшое/среднее | Незначительное | Средняя |
| Колонночная модель | Высокое | Плюс при фильтрах | Средняя |
| Дельта-кодирование | Среднее | Нужен decode | Средняя |
| Varint/base64 | Очень высокое | Небольшая стоимость decode | Высокая |
| gzip/Brotli | Очень высокое при HTTP | Нет | Не решает standalone HTML |

## Итоговая рекомендация

Наиболее разумный баланс:

```text
stripModules
  -> объединение JS
  -> удаление комментариев
  -> минификация JS/CSS
  -> компактный JSON
  -> массивы значений вместо объектов
  -> bitmap для approx
```

При этом интерактивная модель остаётся прежней:

```text
appView.metrics
appView.files
rowModel / cache
DOM table
```

То есть физический размер страницы уменьшается, а обработка кликов не ухудшается. Более того, компактная массивная модель обычно ускоряет `JSON.parse`, снижает расход памяти и облегчает последующий переход к кэшу totals и виртуализации.
