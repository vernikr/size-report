# Производительность кликов по чекбоксам size-report.html

Разбор механизма работы страницы и варианты оптимизации для трёх взаимодействий:

- клик по чекбоксу типа файла (**Код / Документация / Служебные** — строка категорий),
- клик по чекбоксу метрики (**raw / min / tok**),
- клик по чекбоксу **папки** в дереве.

Замеры сделаны на реальном отчёте этого репозитория (`docs/size-report.html`:
**261 файл × 211 коммит × 3 метрики**, таблица 167 893 клетки, панель 304 чекбокса).
Среда замера — jsdom (создание DOM-узлов там медленнее, чем в Chrome, но число
операций над DOM — одинаковое; это и есть главный фактор). Скрипты замера:
`tools/perf/harness-bench.js` (сейчас), `tools/perf/costs.js` (разбивка затрат),
`tools/perf/proto-hide.js` (прототип «прячем, а не пересобираем»).

---

## 1. Как это работает сейчас

### 1.1. Форма артефакта

Страница — один самодостаточный файл без внешних ссылок:

```
<style>      table.css + app.css (дословно)
<script id="data" type="application/json">   1 365 526 символов (99 % веса файла)
<script id="ui"   type="application/json">   словарь интерфейса
<script>      derived.js + src/page/{state,dom,panel,table,app}.js (stripModules)
```

Программа собирается в `src/page/build.js`: листинг глав зашит в `PAGE_PARTS`,
модульный синтаксис снимается построчно (`stripModules`), `derived.js` идёт первой
главой. Контракты, которые это фиксируют: `test/page-view.test.js` (программа
страницы начинается с `derived.js`, список функций закрыт), `test/api.test.js`
(имена API заморожены), `test/contract-derived.test.js` (числа страницы = числа
артефакта, считаются одним `derived.js`).

### 1.2. Модель данных (schema 1)

| Ключ | Что это | Размер |
|---|---|---|
| `rows[r].values[i]` | **плотный** снимок размера файла `i` на коммите `r` (`{raw,min,tok}` или `null`) | **1 274 444 символа — 93 % данных** |
| `files[i]` | label, path, paths, category, categoryBy | 40 467 |
| `catalog` | все пути проекта (для дерева) | 14 373 |
| `now` | абсолютные размеры на HEAD (последний снимок) | 9 133 |
| `approx` | строки битов «клетка приблизительная» (метрика min) | 55 360 |
| `last` | bool «файл тронут последним коммитом» | 1 562 |

Ключевое свойство: `rows` хранит **полный снимок на каждый коммит**, хотя
изменений между соседними коммитами немного. Измерено: непустых пар
(коммит, файл) — 30 331 из 55 071 (55 %), а пар, где размер **действительно
изменился** (включая появления), — всего **1 159** (из 55 071 возможных). Записывать только изменения:
**1 274 444 → 47 819 символов (−26×)**.

### 1.3. Состояние и рендер

```
appView = { metrics: {raw:1, min:1, tok:1}, files: [261 × true], folded: {...} }
```

Любое изменение (категория, метрика, папка, файл) ходит в `appRender()`:

```
appRender()
 ├─ appPanel()   — пересборка ВЕГО панели: дерево из 274 путей (appTree,
 │                 appIndexes/appCount по каждой папке), 304 input, 1 292 узла;
 │                 сохраняют/восстанавливают scrollTop и фокус (по ординалу
 │                 среди querySelectorAll('#panel input'))
 └─ appTable()   — пересборка ВЕГО таблицы: thead + 212 tr;
                   для каждой строки rowModel()/totalsOf() по 261 файлу × 3 метрики;
                   ~167 000 td/th createElement + appendChild
appWrite()       — record + appPassport() (FNV-1a по ~10 КБ: имя, schema,
                   artifact, title, 261 label) + history.replaceState
```

Клик **ничего не переиспользует**: узлы, вычисленные дельты, разметка шапки —
всё уничтожается и строится заново. Это и есть корень проблемы.

### 1.4. Что реально стоит клик (замеры, jsdom)

Разбивка одного рендера:

| Компонент | Время | Доля |
|---|---|---|
| чистая математика: `rowModel` по всем 211 строкам (165 846 клеток) | 34 мс | **0,7 %** |
| `totalsOf` × 422 | 10 мс | 0,2 % |
| `group()` (разряды) по всем непустым значениям × 3 | 47 мс | 1 % |
| `appPanel()` (1 292 узла) | 38 мс | 0,8 % |
| `appTree()` (дерево панели, appIndexes/appCount) | 23 мс | 0,5 % |
| **`appTable()` (167 893 узла)** | **3 431 мс** | **71 %** |
| `appWrite()` (паспорт + replaceState) | 0,6–1,2 мс | 0,02 % |
| **`appRender()` целиком** | **4 806 мс** | 100 % |

Свежая загрузка (HTML-парсинг + `JSON.parse` 1,37 МБ за 10 мс + первый рендер):
**~3,7 с**.

Само взаимодействие (один клик, jsdom):

| Клик | off | on | узлов создано (оба клика) |
|---|---|---|---|
| категория «Код» (105 файлов) | 2 966 мс | 4 086 мс | 279 893 |
| категория «Документация» (139) | 3 149 мс | 4 348 мс | 258 195 |
| метрика raw | 3 775 мс | 4 349 мс | 291 794 |
| папка worklog/ (112 файлов) | 3 393 мс | 4 082 мс | 276 812 |
| **один файл** | 5 270 мс | 7 537 мс | 348 314 |

В реальном Chrome `createElement` быстрее, но число операций то же: это
стабильные **сотни миллисекунд джека на каждый клик** плюс layout таблицы в
787 колонок и GC-давление от 170 000 короткоживущих узлов. У большого проекта
(2000 файлов × 1000 коммитов) один клик — это 6+ млн узлов, то есть
многосекундная заморозка.

**Вывод: ~95 % стоимости клика — создание DOM-узлов, а не вычисления.**
Математика (`derived.js`) за весь рендер тратит < 100 мс и пересчитывать её на
каждый клик вообще не нужно — её результат зависит только от набора
включённых файлов/метрик.

## 2. Варианты оптимизации

Нумерация — по убыванию эффекта. Варианты независимы и складываются.

### 2.1. (ГЛАВНЫЙ) «Прячем, а не пересобираем» таблица строится один раз

Наблюдение, на котором всё строится:

- **содержимое клетки файла** (`+12 345` / `—` / пусто, классы `up`/`down`/
  `miss`, tooltip точности) **не зависит от выбора** читателя — оно статично
  для пары (коммит, файл, метрика). Зависит от выбора только **видимость**
  колонки;
- **порядок колонок тоже статичен**: сортировка «файлы последнего коммита
  первыми» — устойчивая и применяется ко всему списку до фильтрации, поэтому
  «видимая» таблица — это подпоследовательность полной таблицы;
- от выбора зависит только **итог** (212 строк × ≤ 3 метрики = ≤ 636 клеток)
  и пометка приближения итога.

Следовательно:

1. **Полная таблица** (все 261 файл × все метрики, в конечном порядке)
   строится один раз при загрузке (и больше никогда).
2. Клик по файлу/папке/категории = `classList.toggle('off')` на клетках
   колонок + **инкрементальное** обновление итогов:
   `totals[r][m] ±= value(r, i, m)` по строкам, где у файла было значение
   (история снимков самого файла, а не обход всей таблицы).
3. Клик по метрике = один класс-комбо на корне таблицы (2^M = 8 комбинаций):
   CSS прячет всю «дорожку» метрики (тело + thead + строку «сейчас»), JS
   правит только `colSpan` 263 th. Границы групп (класс `g`) — тоже через те
   же 8 правил CSS (в каждой комбинации левую границу несёт первая включённая
   метрика): 8 правил на все случаи, без пересчёта в JS. Граница «итог | первый
   видимый файл» — одна на всю таблицу: при переключении файла класс `g`
   сдвигается на первые клетки/заголовки нового первого видимого файла
   (≤ 2×212 classToggle, и только если выбор действительно сместил границу).
4. Пометка приближения итога (worst-of-ON): предсчитать для каждой
   (строки, метрики) множество помеченных файлов; при переключении файла
   поддерживать счётчик «включено помеченных» на (строка, метрика) — O(строки)
   на файл. Клетки-файлы: при скрытии колонки снимать класс `approx`
   (`toggle('approx', marked && !off)`) — семантика «выключенного нет ни в
   таблице, ни в пометках» сохраняется как сейчас.
5. Пустые состояния: 0 метрик → `#shell.hidden` (один класс, сетка на месте);
   0 файлов → итоговые колонки + поясняющий текст (как сейчас).

**Замеры прототипа** (jsdom, та же страница, та же полная таблица;
`tools/perf/proto-hide.js`):

| Взаимодействие | сейчас | hide | ускорение |
|---|---|---|---|
| один файл | 5 270–7 537 мс | **9,4–16 мс** | **~450×** |
| категория «Служебные» (17) | 3–4 с\* | **71–95 мс** | ~40× |
| категория «Код» (105) | 2 966–4 086 мс | **444–507 мс** | ~7× |
| категория «Документация» (139) | 3 149–4 348 мс | **599–1 149 мс** | ~4× |
| папка worklog/ (112) | 3 393–4 082 мс | **455–491 мс** | ~7× |
| метрика raw | 3 775–4 349 мс | **1,6–3,6 мс** | **~1 500×** |

\* не замерялась отдельно: полный rebuild не зависит от размера группы,
все категории стоят ~3–4,3 с (см. таблицу выше).

В Chrome разница ещё больше в пользу hide: jsdom медленный именно в
`classList`/атрибутах, а 67 000 `classList.toggle` в Chrome — это 10–30 мс.
Остаточная стоимость группового клика пропорциональна
`(файлов в группе) × (строк) × (метрик)` — для отчёта этого размера это
миллисекунды.

Что это даёт по трём запрошенным взаимодействиям:

- **Код/Документация/Служебные**: N переключений файлов = N × 636 classToggle
  + один проход по 636 итоговым клеткам (textContent + класс up/down).
  Ноль новых узлов.
- **raw/min/tok**: 1 classList на таблице + 263 colSpan. ~1000× быстрее.
- **Папка**: как категория, только N = размер поддерева; индексы поддеревьев
  считаются один раз при загрузке (сейчас `appIndexes` пересчитывается для
  каждой папки на каждый рендер).

Ограничения (честно):

- Таблица целиком живёт в DOM всегда (167 893 клетки). Для этого отчёта это
  нормально; для 2000 файлов × 1000 строк (6,4 млн клеток) — уже нет. Тогда
  нужны 2.5 и/или 2.6 (виртуализация/грид).
- Layout-проход после клика покрывает всю ширину таблицы (одна пересчитка
  стиля по 168k узлов). В Chrome это десятки миллисекунд — приемлемо, но это
  «пол» подхода; убрать его может только уменьшение числа узлов (2.6).
- **Сознательные изменения контрактов тестов** (всё можно менять, но
  осознанно):
  - `page-view` «без метрик — таблица всё ещё строится»:
    `querySelectorAll('#grid tbody tr').length === 0` — при hide строки
    остаются (таблица скрыта классом). Фикс: проверять `#shell.hidden` +
    видимость, а не отсутствие tr.
  - `page-view` «без файлов в строке остались чужие колонки»:
    `querySelectorAll('td').length === metrics.length` — теперь td скрыты, а
    не отсутствуют. Фикс: считать видимые.
  - `page-view` «с точными слагаемыми остались помеченные клетки»: при hide
    скрытые клетки несут статический класс `approx` — см. пункт 4 выше
    (снимать класс при скрытии), тест при этом работает без изменений.
  - `page-choice`, `page-tree` — поведение не меняется.

### 2.2. Панель обновлять на месте (вместо пересборки)

Структура панели статична: набор чекбоксов (304) не меняется между рендерами —
меняются только `checked`/`indeterminate`. Значит:

- панель строится один раз;
- клик по файлу: `input.checked = …` для самих файлов (261 запись) +
  пересчёт `checked`/`indeterminate` у папок и категорий из **предвычисленных
  списков индексов** (категория: 3 × 261 проверок; папки: Σ размеров
  поддеревьев ≈ 1,4 тыс. проверок);
- **фокус**: узел с фокусом не уничтожается → фокус сохраняется сам собой.
  Текущий подход «запомнить ординал, пересобрать, вернуть по ординалу»
  (`querySelectorAll('#panel input')` до и после) — убирается;
- **скролл**: `scrollTop` не сбрасывается → `appScrollTop`/`appScrollBack`
  убираются.

Эффект: рендер панели 38 мс → < 2 мс; стабильнее поведение клавиатуры
(текущий «ординал» — хрупкий: он вернёт фокус на *другой* чекбокс, если
порядок когда-нибудь изменится).

### 2.3. Формат данных страницы: разреженные строки (schema 2)

(Тот же формат рассматривается отдельно — через призму **физического размера
файла** — в `page-size.md`.)

`rows` — 93 % веса файла, из них 96 % — «шум» (неизменённые значения
дублируются из строки в строку). Разреженная модель:

```js
// строка: только изменившиеся/появившиеся файлы
rows: [ { sha7, when, subject, section, href,
          c: { <fileIdx>: {raw, min, tok} } } ]

// файл: история размеров (каждое изменение + помётка точности min)
files: [ { label, path, paths, category, categoryBy,
           s: [ [row, {raw,min,tok}, approxBit], … ] } ]

// presence: интервалы [startRow, endRow] (в этом отчёте у каждого файла
// один интервал — исчезновений с возвратом нет; в общем — список
// интервалов, как в тесте GAPS с crlf.txt)
```

Замеры на реальном отчёте:

| | сейчас (schema 1) | sparse (v2, наивно) |
|---|---|---|
| вес данных в файле | 1 334 КБ | **157 КБ** |
| `JSON.parse` | 10 мс | **2,4 мс** |
| `rows` в JSON | 1 274 444 симв. | 47 819 симв. |

Дальше можно ужать словарь значений (уникальных кортежей
`{raw,min,tok}` всего **1 159**) и биты presence (211×261 бит = 6,7 КБ),
получив ~110 КБ, но и наивных 157 КБ достаточно.

Важно для контрактов:

- **Формат `--json`/`--data` не трогаем** — он запарирован с эталоном
  legacy-инструмента (`fixtures/parity`, `tools/parity-freeze.js` сравнивает
  побайтово). Меняется только payload страницы (`pagePayload()` — уже отдельный
  билдер со своим списком исключений `NOT_IN_FILE`); ему поднимается
  `schema: 2`.
- Страница **сохраняет `derived.js` как единственный вычислитель** (требование
  `page-view`): `state.js` после парсинга v2 за O(изменений) восстанавливает
  плотные снимки (или сразу строки-модели) и работает в привычной модели.
  То есть формат прозрачен для контрактов чисел: `rowModel`/`totalsOf`
  получают те же значения, `contract-derived` не меняется.
- Паспорт записи выбора включает `schema` — старые записи localStorage/ссылок
  для новой страницы не применятся (gracefully: «чужая» запись игнорируется,
  правило уже есть в `appRecordOk`).
- `approx` (55 360 симв.) сворачивается в биты истории файла (`s[…][2]`):
  помётка точности меняется только вместе с файлом — проверить по данным
  (в текущем отчёте: да, бит неизменен, пока файл неизменён).
- `now` (9 КБ) становится избыточным (последний снимок `s`) — убирается из
  payload; терминальный `--json` его хранит дальше.

### 2.4. Мелкие, но бесплатные

1. **Кэшировать `appPassport()`** — константа отчёта (FNV-1a по ~10 КБ +
   `files.map` + `join` на каждый `appWrite` → 0,3–0,6 мс × каждый клик).
2. **Дебаунс `history.replaceState`** (150–300 мс): запись в адрес на каждый
   клик — лишняя операция истории; 300 мс читатель не заметит, а ссылка
   остаётся актуальной.
3. **`group()` по словарю**: отформатировать 1 159 уникальных значений один
   раз при загрузке (сейчас 47 мс регулярки только на старте; при 2.1
   пересчёта на кликах не будет вовсе).
4. **Делегирование событий** на панели: один `change`-listener на `#panel`
   вместо 304 (гигиена + меньше памяти; при 2.2 слушателей вообще ноль).
5. **Строковое построение при загрузке**: сборка строки таблицы на 166 632
   клетки — 3 мс (замер). В jsdom `innerHTML` *медленнее* `createElement`
   (5,0 с против 3,4 с — медленный парсер jsdom), в Chrome обычно быстрее;
   в любом случае это один разовый эффект против 2.1/2.3, выбирать
   по бенчмарку в реальном браузере.

### 2.5. Масштаб: виртуализация строк (когда коммитов много)

211 строк — мелочь, но реальные проекты дают тысячи. Видимая часть скролла
(~30–40 строк) живёт в DOM, остальное не строится:

- DOM: 167 893 → ~25 000 клеток (7×), initial render и layout проходы
  пропорционально дешевле;
- клики: классы/тексты только по видимым строкам (10–15× меньше работы);
- «сейчас» — всегда на виду (первая строка), sticky-шапка — над окном;
- совместимо с 2.1 (видимость колонок) и 2.3 (разреженные строки — windowing
  по ним делается по индексу, без плотных снимков).

Цена: windowing-логика, синхронизация скролла, корректная позиция вёрстки
липкой первой колонки. Отдельный, самый большой пласт работы — только
нужен, когда появятся отчёты 1000+ строк.

### 2.6. Масштаб: колонки как контейнеры (CSS grid)

Альтернатива/дополнение 2.1 для огромных таблиц: «колонка файла» = один
контейнер (div-grid вместо `<table>`), переключение файла = **1**
`classList.toggle` независимо от числа строк (105 файлов категории = 105
операций против 67 000).

Цена серьёзная: теряется семантика нативной таблицы (экраны доступа,
колонки-заголовки) — нужны `role="table|row|columnheader"` и aria-связи;
перепишется общая часть `table.css`, которая вшита в артефакт дословно и
проверяется побайтово (`page-view`: `TABLE_CSS` в странице ровно один раз).
Брать только если 2.5 покажется недостаточно.

## 3. Что делать (порядок)

**Этап 1 — максимум эффекта при нуле риска для чисел** (страница, данные
не трогаем): 2.1 + 2.2 + мелочи 2.4.1–2.4.4.
Ожидаемо: клик по файлу ~450×, категория/папка 4–40× (jsdom; в браузере
миллисекунды без джека), метрика ~1500×. Контракты чисел (`contract-*`)
не тронуты; правятся 2–3 утверждения `page-view` про «строки исчезли» →
«строки скрыты» (см. 2.1, ограничения).

**Этап 2 — размер и загрузка**: 2.3 (sparse v2 payload, schema 2, плотное
восстановление в `state.js`). Файл −88 %, загрузка быстрее, контракты чисел
опять же не тронуты.

**Этап 3 — масштаб** (по мере появления больших отчётов): 2.5, при
необходимости 2.6.

После этапа 1+2 структура стоимости клика:

| | сейчас | после (оценка) |
|---|---|---|
| один файл | ~3–7 с (jsdom) | ~1–5 мс JS + маленький layout |
| категория/папка (≤ 112 файлов) | ~3–4 с | ~50–200 мс (jsdom) / десятки мс (Chrome) |
| метрика | ~4 с | ~1–5 мс |
| DOM-узлов создано за клик | ~170 000 | **0** |
| размер отчёта | 1,44 МБ | ~160 КБ |
| `JSON.parse` | 10 мс | ~2,4 мс |
