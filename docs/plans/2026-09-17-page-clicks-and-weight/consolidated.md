# Сводный отчёт: отклик чекбоксов и вес `size-report.html`

Сведение шести исходных отчётов в один непротиворечивый план. Все расхождения между
источниками вынесены в раздел 5 и разрешены замером; всё, что здесь утверждается
числом, получено скриптами из `tools/perf/` на актуальном артефакте.

| Источник | О чём |
|---|---|
| `uploads/performance-1.txt` | Клики: разбор механики, замеры в jsdom, прототип «прячем, а не пересобираем», схема payload v2 |
| `uploads/performance-2.txt` | Клики: разбор по типам взаимодействий, варианты A–E (кэш, частичный рендер, виртуализация, модель данных, Worker) |
| `uploads/performance-3.txt` | Клики: замеры в Chrome, три яруса оптимизаций, ограничения репозитория |
| `uploads/page-size-1.txt` | Вес: **исполняемый прототип** payload v3 (разреженная история файла) с проверкой беспотерьности |
| `uploads/page-size-2.txt` | Вес: 14 приёмов (минификация, компактный JSON, колонночная модель, bitmap, varint, gzip) |
| `uploads/page-size-3.txt` | Вес: замер блоков текущего файла, словарь + события, slim-мета, итоговая лестница |

## 0. Условия задачи и что они отменяют

Задано заказчиком:

1. **Менять можно всё, включая формат и модель исходных данных.**
2. **Разделение значений на точные и приблизительные (подчёркнутые) выпиливается полностью.**
3. **Совместимость с текущими тестами не важна.**

Что из-за этого снимается с рассмотрения:

- Все оговорки источников про «нельзя сломать контракт» теряют силу: правки
  `test/page-view.test.js` про «строки исчезли» → «строки скрыты» (перечислены в
  `performance-1.txt`, §2.1), требование «страница считает только общим расчётом»
  (`performance-3.txt`, §4), запрет менять `schema` без версии.
- Всё, что касалось `approx`/`accuracy` как оптимизация (bitmap-упаковка из
  `page-size-2.txt` §8, предындексация карты приближений из `performance-3.txt` §4.3),
  превращается в простое удаление. Экономия: **56 310 байт** данных, 127 байт
  словаря `#ui` и ~336 000 посимвольных чтений `charAt` за рендер (см. §3).
- `performance-3.txt` прямо опирается на «тесты не позволят считать по-своему» —
  это ограничение больше не действует, и инкрементальные итоги можно вести как
  отдельный быстрый слой.

Что **остаётся** в силе, потому что это не тесты, а свойства продукта:

- **Самодостаточность файла**: страница открывается двойным щелчком с диска, без сети
  и без внешних ссылок (`docs/size-report.html`, `src/page/build.js`). Это исключает
  внешние скрипты и ставит под вопрос Web Worker (раздел 6).
- **Неподвижная точка артефакта**: отчёт пересобирается хуком после каждого коммита и
  коммитится сам (`.githooks/post-commit`). Сборка обязана быть побайтово
  воспроизводимой на любой машине — это ограничивает выбор минификатора (раздел 4.3).

## 1. Единая картина: как страница устроена и почему клик дорогой

Три отчёта описывают один и тот же механизм и расходятся только в числах. Ниже —
согласованное описание, сверенное с кодом.

### 1.1. Артефакт

Один файл, 1 467 578 байт (1433,2 КиБ). Все числа здесь и дальше — в КиБ (1024).

| Блок | Байт | Доля |
|---|---:|---:|
| Данные `#data` | 1 394 518 | 95,0 % |
| Программа (6 глав исходников, вклеенных построчно) | 50 759 | 3,5 % |
| CSS (`table.css` + `app.css` дословно) | 19 254 | 1,3 % |
| Словарь интерфейса `#ui` | 2 330 | 0,2 % |
| Оболочка и разметка | 717 | 0,05 % |

Программа собирается в `src/page/build.js`: список глав зашит в `PAGE_PARTS`
(`state.js`, `dom.js`, `panel.js`, `table.js`, `app.js`), первой идёт `derived.js`,
модульный синтаксис снимается построчно (`stripModules`). Комментариев в вклеенной
программе ~30 311 байт из 50 759, в CSS ~13 384 из 19 254.

### 1.2. Данные (schema 1)

213 строк истории × 263 файла × 3 метрики (raw/min/tok).

| Ключ | Байт | Доля данных | Что это |
|---|---:|---:|---|
| `rows` | 1 270 882 | 91,1 % | из них `values` — 1 205 268 (86,4 % данных, 83,6 % файла), мета строк — 65 614 |
| `approx` | 56 310 | 4,0 % | битовые строки, только для метрики `min` |
| `files` | 40 782 | 2,9 % | label, path, paths, category, categoryBy |
| `catalog` | 14 480 | 1,0 % | 276 путей проекта для дерева |
| `now` | 9 200 | 0,7 % | абсолютные размеры на HEAD |
| `last` | 1 574 | 0,1 % | какие 5 колонок тронуты последним коммитом |
| прочее | 1 183 | 0,1 % | `metrics`, `report`, `categories`, `tool`, `schema` |

Главное свойство, на котором держится вся экономия веса — **избыточность снимков**:

- клеток 213 × 263 = 56 019, из них непустых 30 856, `null` — 25 163;
- **уникальных троек `{raw,min,tok}` — 1 169** (3,8 % от непустых);
- клеток, отличающихся от предыдущей строки, — **1 165**, то есть 5,5 изменения на коммит;
- записей в модели «история файла» (сколько раз значение действительно менялось) — **1 169**.

Прочие проверенные факты, на которые опирается план:

- `now` **в точности равен** `values` последней строки (проверено сравнением). Это
  структурно: строка появляется только когда объём изменился (`src/history.js:119`),
  её `cells` — это срез общего состояния (`:130`), а `state` на выходе — оно же (`:174`).
  Значит `now` — 9 200 байт чистого дублирования.
- `href` у всех 213 строк = один и тот же префикс + полный 40-символьный `sha`, который
  уже лежит в поле `sha`. То есть sha хранится **дважды**, а короткий sha не хранится
  вовсе — его режет `derived.js:101`.
- 253 метки из 263 совпадают с basename пути; 10 отличаются (одинаковые имена в разных
  папках: `README.md`, `config.json`, `metrics.js` и т. п.). Файлов без `path` в этой
  сборке нет.
- 263 записи каталога из 276 совпадают с путём колонки → их можно заменить индексом
  колонки; непустой `why` всего у 13.

### 1.3. Конвейер клика

Любой чекбокс — файл, папка, категория, метрика — меняет один флаг в `appView` и
вызывает один и тот же `appRender()` (`src/page/app.js:58`):

```
appRender()
 ├─ запомнить фокус по ординалу среди querySelectorAll('#panel input')
 ├─ appScrollTop()
 ├─ appPanel()          — panel.textContent = '' (panel.js:170) и 306 инпутов заново
 ├─ appScrollBack() + возврат фокуса
 └─ appTable()          — table.textContent = '' (app.js:21)
      ├─ appHead()      — thead: 265 th первой строки + 792 th второй
      ├─ appBody()      — 213 строк × rowModel() + строка «сейчас»
      └─ appWrite()     — паспорт (FNV-1a), localStorage, history.replaceState
```

Ничего не переиспользуется: узлы, посчитанные дельты, разметка шапки — всё
уничтожается и строится заново. Единственное исключение — знак сворачивания папки
(`panel.js:82`): он меняет класс на строке и не вызывает рендер. Это и есть образец
целевого поведения.

Раскладка готовой таблицы: **216 строк, 170 759 клеток**, 177 163 узла в документе;
панель — 306 инпутов, 1 300 узлов.

**Согласованный диагноз (все три отчёта правы в главном):**

> ~95 % стоимости клика — создание и разрушение DOM-узлов, а не вычисления.
> Математика всего рендера — 32,6 + 63,6 мс, то есть **~2 %**. Пересчитывать её на
> каждый клик не нужно вовсе: результат зависит только от набора включённых
> файлов и метрик, а сами данные за время жизни страницы не меняются.

Из этого следует, что `performance-2.txt` верно описывает механизм, но неверно
расставляет приоритеты (раздел 5, п. 9).

## 2. Целевое решение

Четыре этапа. Первые три независимы и складываются; четвёртый — по мере роста истории.

### Этап 1. Рендер: строить один раз, переключать видимость

Основание (проверено по коду):

- **содержимое клетки файла** (`+12 345` / `—` / пусто, классы `up`/`down`/`miss`)
  зависит только от пары (коммит, файл, метрика) и не зависит от выбора читателя;
- **порядок колонок статичен**: сортировка «файлы последнего коммита вперёд»
  (`app.js:18`) устойчивая и её ключ зависит только от файла, поэтому видимая таблица —
  всегда подпоследовательность полной;
- от выбора зависят только **видимость колонок**, **итоги** (214 строк × ≤3 метрики)
  и положение границы групп.

#### 1.1. Таблица-супермножество

Полная таблица (все 263 файла × все 3 метрики, в конечном порядке) строится один раз
при загрузке и больше не пересобирается. Клик по файлу/папке/категории — класс на
клетках его колонки.

#### 1.2. Кэш ссылок на клетки — условие, без которого приём не работает

Это самая важная деталь всего плана, и в источниках она названа только у
`performance-2.txt` (B4: «лучше хранить ссылки, а не `querySelectorAll` на каждый клик»).
Замер `tools/perf/micro-dom.mjs`:

| Приём | Стоимость переключения одной колонки (642 клетки) |
|---|---:|
| Обход `tr.children[i]` каждый раз | 70,5 мс |
| Заранее собранные ссылки на клетки | **6,2 мс** |

Одна операция в jsdom: `classList.toggle` 0,0070 мс, `textContent` 0,0126 мс,
**чтение `tr.children[i]` 0,0254 мс**, `group()` 0,0010 мс. То есть наивная реализация
тратит большую часть времени на доступ к детям строки, а не на сами переключения.

В реальной правке кэш собирается бесплатно — при первом построении таблицы каждый `td`
и так создаётся, ссылку достаточно положить в массив. (В прототипе
`tools/perf/proto-hide.mjs` обход уже готового DOM обошёлся в 2 924 мс — это цена
прототипа, а не решения.)

#### 1.3. Метрики: класс на корне таблицы

Дорожка метрики прячется одним классом на `#grid` (2³ = 8 комбинаций, 8 правил CSS),
плюс `colSpan` у 265 th шапки. Альтернатива — перебор клеток метрики — дороже на два
порядка:

| Приём | off | on | Операций |
|---|---:|---:|---:|
| Класс на `#grid` + `colSpan` | 2,20 мс | 1,37 мс | 265 |
| Перебор клеток метрики | 433,15 мс | 438,53 мс | 56 496 |

Границы групп (класс `g`) — теми же 8 правилами CSS: в каждой комбинации левую границу
несёт первая включённая метрика. Граница «итог | первый видимый файл» одна на таблицу:
при переключении файла класс переезжает на клетки нового первого видимого файла.

#### 1.4. Итоги инкрементально

Итог линеен: дельта суммы равна сумме дельт включённых. Значит при переключении файла
достаточно `totals[m][r] ±= value(r, i, m)` по тем строкам, где у файла было значение
(история снимков самого файла), и перезаписать ≤3 итоговых клетки строки. Стоимость
переключения файла — O(строк × метрик) вместо O(строк × файлов × метрик); для папки
из K файлов — O(строк × K × метрик).

Дельты и тексты клеток готовятся один раз при загрузке: их 1 169 уникальных значений,
форматирование `group()` всех непустых клеток × 3 метрики стоит 63,6 мс **один раз**
вместо тех же 63,6 мс на каждый клик.

#### 1.5. Панель обновляется на месте

Структура панели статична — 306 чекбоксов не меняются между рендерами, меняются только
`checked`/`indeterminate`. Панель строится один раз; клик по файлу правит его чекбокс и
состояния предков из предвычисленных списков. Заодно исчезают два обходных механизма:
восстановление скролла (`appScrollTop`/`appScrollBack`) и возврат фокуса по ординалу —
узел с фокусом больше не уничтожается. Индексы категорий и папок (`appIndexes`,
`panel.js:28`) считаются один раз: сейчас `panel.js:133` обходит каждое поддерево, чтобы
узнать, есть ли в нём колонки, а `panel.js:52` обходит его же ещё раз.

#### 1.6. Мелочи, которые становятся заметны после этапа 1

- Кэш `appPassport()` — константа отчёта, сейчас считается на каждый `appWrite` (0,6 мс).
- Дебаунс `history.replaceState` на 150–300 мс (сейчас `appWrite` = 4,0 мс на клик;
  после этапа 1 это уже ~15 % оставшейся стоимости клика).
- Делегирование `change` на `#panel` вместо 306 слушателей (`dom.js:17`) — при панели
  на месте это только гигиена.

#### 1.7. Что даёт этап 1 (замер `tools/perf/proto-hide.mjs`, jsdom)

| Взаимодействие | Сейчас | Прототип | Ускорение |
|---|---:|---:|---:|
| Один файл | 5 879 / 5 662 мс | **30,5 / 27,2 мс** | **193×** |
| Категория «Служебные» (17) | ~3–4 с | **244 / 216 мс** | ~15× |
| Категория «Код» (105) | 3 160 / 5 907 мс | **1 328 / 1 211 мс** | ~2,4× |
| Папка `worklog/` (114) | 3 645 / 4 146 мс | **944 / 861 мс** | ~3,9× |
| Метрика (класс на корне) | 3 760 / 4 647 мс | **2,2 / 1,4 мс** | **~1 710×** |
| Узлов создано за клик | ~170 000 | **0** | — |

Остаточная стоимость группового клика пропорциональна
(файлов в группе) × (строк) × (метрик): 105 файлов категории «Код» — это 120 645
точечных правок, отсюда 1,3 с в медленном jsdom. В Chrome точечные правки на порядок-два
дешевле (не измерялось здесь), но именно поэтому для больших групп имеет смысл этап 4.

### Этап 2. Формат данных: schema 2 (разреженная история файла)

Модель из `uploads/page-size-1.txt` — она же `tools/perf/proto-payload-encode.mjs`.
**Беспотерьность проверена на актуальном артефакте**: обратное развёртывание даёт
побайтово равные `tool`, `report`, `metrics`, `categories`, `files`, метаданные строк,
все 56 019 клеток `values`, `now`, `last`, `catalog` (`round-trip: LOSSLESS ✓`).

Суть модели: вместо снимка на каждый коммит — история каждого файла.

```js
rows:  [ [sha, when, subject, section?, href?] ]        // без values
files: [ [label, path, paths, category, categoryBy,
          [ [row, dRaw, dMin, dTok, approxBit?] ] ] ]   // только изменения
strs:  [ … ]                                            // словарь строк, ссылки индексами
```

Первое появление файла несёт абсолютные значения, остальные записи — приращение.
Словарь строк убирает повторение путей, меток и подписей. `href` сворачивается в
префикс + sha, `last` — в список индексов, `catalog` — в индекс колонки там, где путь
совпадает, `now` **исчезает** (восстанавливается из последней строки, см. §1.2).

| Замер (`tools/perf/size-ladder.mjs`) | Значение |
|---|---:|
| Блок данных сейчас | 1 361,8 КиБ |
| Блок данных v3, без `approx` | **81,3 КиБ** |
| Блок данных v3, с `approx` (для сравнения) | 84,6 КиБ |
| Развёртывание v3 в плотную модель (JSON.parse + сборка) | **3,9 мс** (с `approx` 6,1 мс) |
| `JSON.parse` текущих данных | 10,3–11,0 мс |

Важно для порядка работ: развёртывание v3 даёт ровно ту плотную модель, которую читает
расчёт, поэтому `rowModel`/`totalsOf`/`cellParts` остаются единственными
вычислителями чисел. Формат прозрачен для чисел — меняется только то, что лежит в файле.

Формат `--json`/`--data` при этом можно не трогать: он запарирован с эталоном
(`fixtures/parity`, `tools/parity-freeze.js`), а payload страницы собирается отдельно
(`pagePayload()`, `src/page/build.js:101`, со своим списком исключений `NOT_IN_FILE`).
Поднимается `schema: 2`; старые записи выбора в localStorage и старые ссылки становятся
«чужими» — страница уже умеет их отклонять (`appRecordOk`, `src/page/state.js:93`).

### Этап 3. Вес артефакта: комментарии и минификация

Замер `tools/perf/asset-weight.mjs`:

| Приём | JS | CSS | Вместе |
|---|---:|---:|---:|
| Сейчас | 49,6 КиБ | 18,8 КиБ | 68,4 КиБ |
| Убрать комментарии (своим кодом, без внешних пакетов) | 19,8 КиБ | 5,7 КиБ | **25,5 КиБ** |
| Минификация esbuild | 13,5 КиБ | 4,7 КиБ | **18,2 КиБ** |

Удаление комментариев даёт **42,9 КиБ из 50,1 КиБ** достижимой экономии — 86 % эффекта
без единой новой зависимости. esbuild добавляет сверху 7,3 КиБ.

Минификация не меняет расчёт — проверено: `derived.js` 5 127 → 1 353 байт, `rowModel`
даёт побайтово равный результат по всем 213 строкам (168 057 клеток), `group(1234567)`
и `cellParts(5, -3)` совпадают.

Порядок вклейки важен (`page-size-2.txt` §1 прав): `stripModules` снимает модульный
синтаксис построчно, поэтому сначала склейка и снятие модулей, потом сжатие, потом
вклейка в HTML.

### Этап 4. Масштаб: виртуализация строк (когда история вырастет)

213 строк — не проблема; тысячи строк — проблема. В DOM держатся только видимые
~30–40 строк плюс распорки сверху и снизу:

- клетки: 170 759 → ~25 000, стартап и раскладка пропорционально дешевле;
- точечные правки на клик — только по видимым строкам;
- стартап перестаёт зависеть от длины истории.

Совместима с этапом 1 (видимость колонок) и этапом 2 (окно по разреженной истории
берётся по индексу). Цена: оконная логика, синхронизация скролла, липкая первая колонка,
доступность, поиск по странице и печать. Дешёвая проба перед этим —
`content-visibility: auto` на строках, но для таблиц он требует
`table-layout: fixed`.

Брать этап 4 имеет смысл, когда появятся отчёты на 1000+ строк: после этапов 1–3 клик
по метрике стоит 2 мс, а по категории из 105 файлов — 1,3 с в jsdom и, по всей
видимости, десятки-сотни миллисекунд в Chrome.

## 3. Что уходит вместе с `approx`

Удаление признака точности — сквозная правка, а не одна строка. По слову `approx`/
`accuracy` в исходниках: `metrics.js` (23), `table.js` (14), `data.js` (6),
`history.js` (4), `state.js` (4), `locales.js` (4), `doctor.js` (3), `modes.js` (3),
`tokens.js` (3), `page/build.js` (2), `check.js`, `init.js`, `minify.js`, `project.js`,
`strip.js`, `page/panel.js` (по 1). Упоминается в шести файлах тестов.

Что это даёт сверх самой функциональности:

- −56 310 байт данных и 127 байт словаря `#ui` (ключи `exact`, `approximate`, `approxCell` — из 2 330 байт и 22 ключей);
- −336 000 посимвольных `charAt` за рендер: `appApprox` (`table.js:9`) для каждой
  итоговой клетки проходит по всем включённым файлам (3 × 263) и для каждой клетки
  файла читает один символ (263 × 3) — 1 578 чтений на строку × 213 строк;
- из модели v3 исчезает флаг точности в записи истории (−3,3 КиБ: 84,6 → 81,3 КиБ).

## 5. Что отброшено и почему

| Приём | Источник | Почему не берём |
|---|---|---|
| `DocumentFragment` | `performance-2` A4 | Уже фактически есть: строки строятся в отсоединённом `tbody` |
| Перевод `forEach` на `for` в горячих циклах | `performance-2` A3 | Математика — 0,7 % клика; экономить нечего |
| Колонночная модель на typed arrays как способ **сжать файл** | `performance-2` D1, `page-size-2` §5 | Как формат хранения в JSON не компактнее v3 (проверено: v3 даёт 81,3 КиБ). Как представление **в памяти** после развёртывания — полезно и берётся в этапе 2, но это уже не про вес |
| Varint/base64 для чисел | `page-size-2` §10 | Свой бинарный формат и потеря читаемости ради КиБ, которые даёт обычный gzip. Рассматривать только если 62 КиБ всё ещё много |
| Готовая HTML-таблица в файле | `page-size-2` §12.2 (как антирекомендация) | Подтверждено: разметка в разы тяжелее данных, итоги без данных не пересчитать |
| Web Worker | `performance-2` E | Самодостаточность с диска под вопросом (п. 21), а после этапа 1 считать на клик почти нечего |
| Колонки-контейнеры вместо `<table>` (CSS grid) | `performance-1` §2.6 | Теряется семантика таблицы и доступность, переписывается вклеиваемый дословно `table.css`. Запасной путь, если виртуализации окажется мало |
| Префиксы путей | `page-size-2` §6.3 | Словарь строк v3 уже убирает повторение путей; усложняет дерево |
| Упаковка `approx` в bitmap | `page-size-2` §8 | Признак точности выпиливается |
| Ленивый кэш дельт | `page-size-2` §7 | При «строим один раз» дельты нужны сразу и один раз; лень добавит ветвлений без выгоды |

## 7. Непроверенное

Честно, что в этом отчёте не подтверждено замером:

- **Все числа про Chrome.** Замеры здесь — jsdom 26 на Node 22.22.3. jsdom заметно
  медленнее браузера в создании узлов и в `classList`, поэтому абсолютные миллисекунды
  в Chrome будут меньше; отношение «пересборка против точечной правки» при этом
  сохраняется, потому что число операций то же.
- **Поведение `visibility: collapse` на `<col>`** (предложение `performance-3`) — в
  разных браузерах по-разному, нужен живой браузер. Запасной путь — класс на клетках,
  он и замерен.
- **Web Worker с `file://`** — см. п. 21.
- **`innerHTML` против `createElement`** при стартовом построении — см. п. 14.
- **Стоимость прохода раскладки** после точечной правки: прототип мерил только JS. В
  Chrome правка классов на 642 клетках вызовет пересчёт стиля; это «пол» подхода, и
  убирается он только уменьшением числа узлов (этап 4).
- Скрипты замеров (`tools/perf/`) написаны для этого отчёта и **не прогонялись через
  гейты репозитория** (`check:standards`, сенсор раздувания, сенсор покрытия).
