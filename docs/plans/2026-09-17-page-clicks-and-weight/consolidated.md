# Отклик чекбоксов и объём `size-report.html`

Разбор того, что делает страница на клик по фильтру, и план из четырёх этапов: клик
перестаёт пересобирать таблицу, данные переходят в разреженную модель, артефакт
худеет, а рост истории перестаёт влиять на скорость. Числа сняты скриптами из
`tools/perf/` на артефакте этого репозитория; как воспроизвести — в конце.

Стенд: jsdom 26, Node 22.22.3, артефакт 1 467 578 байт (213 коммитов × 263 файла ×
3 метрики). jsdom заметно медленнее браузера в создании узлов и в правке классов,
поэтому абсолютные миллисекунды в Chrome будут меньше; число операций при этом то же,
а выводы построены на числе операций.

## 1. Как страница устроена сейчас

### 1.1. Артефакт

### 1.3. Что происходит на клик

Любой чекбокс — файл, папка, категория, метрика — меняет один флаг в `appView` и
вызывает один и тот же `appRender()` (`src/page/app.js:58`):

```
appRender()
 ├─ запомнить фокус по его порядковому номеру среди querySelectorAll('#panel input')
 ├─ appScrollTop()                     — снять прокрутку панели
 ├─ appPanel()                         — panel.textContent = '' (panel.js:170) и 306 инпутов заново
 ├─ appScrollBack() + вернуть фокус
 └─ appTable()
      ├─ table.textContent = ''        (app.js:21)
      ├─ appHead()                     — thead: 265 th в первой строке, 792 th во второй
      ├─ appBody()                     — 213 строк, в каждой rowModel(), плюс строка «сейчас»
      └─ appWrite()                    — паспорт, localStorage, history.replaceState
```

Ничего не переиспользуется: узлы, посчитанные дельты, разметка шапки — всё
уничтожается и строится заново. Порядок колонок при этом каждый раз сортируется
одним и тем же устойчивым правилом (`app.js:18`), а `appIndexes` обходит каждое
поддерево дважды — один раз в `panel.js:133`, чтобы узнать, есть ли в папке колонки, и
второй раз в `panel.js:52`, чтобы собрать её файлы.

Единственное исключение — знак сворачивания папки (`panel.js:82`): он меняет класс на
строке дерева и не вызывает рендер. Это образец того, как должны работать все фильтры.

Готовая таблица: **216 строк, 170 759 клеток**, 177 163 узла в документе. Панель —
306 инпутов, 1 300 узлов.

### 1.5. Диагноз

`appTable()` — 3 904 мс из ~4 800 мс рендера, то есть **81 %**. Вся математика рендера —
32,6 + 63,6 = 96 мс, то есть **2 %**. Пересборка панели — 28,9 мс, **0,6 %**: по времени
она ничего не стоит, но именно она заставляет вручную сохранять и возвращать прокрутку
и фокус.

> Стоимость клика — это создание и разрушение DOM-узлов, а не вычисления.
> Числа зависят только от набора включённых файлов и метрик, а данные за время жизни
> страницы не меняются. Значит таблицу можно построить один раз, а дальше — только
> показывать и прятать колонки и править итоги.

Из этого же следует, что кэширование расчётов само по себе ничего не даёт: экономить
2 % бессмысленно. Инкрементальные итоги нужны не как ускорение счёта, а как способ
обновить итоги, не пересобрав таблицу.

## 2. Этап 1. Рендер: строить один раз, переключать видимость

### 2.1. Почему это возможно

Три инварианта, все три видны в коде:

1. **Содержимое клетки файла не зависит от выбора читателя.** Что написано в клетке
   (`+12 345`, пусто, `—`) и какого она цвета, определяется парой (коммит, файл) и
   метрикой — `cellParts` в `derived.js:46`. Выбор читателя влияет только на то,
   видна ли колонка.
2. **Порядок колонок статичен.** Сортировка «файлы последнего коммита вперёд»
   (`app.js:18`) устойчивая, а её ключ зависит только от файла, а не от выбора.
   Поэтому видимая таблица — всегда подпоследовательность полной, и прятать колонки
   можно, не переставляя их.
3. **От выбора зависят только итоги** (214 строк × ≤3 метрики = ≤642 клетки) и то,
   какие колонки видны.

### 2.2. Разметка полной таблицы

Таблица строится один раз при загрузке — все 263 файла × все 3 метрики, в конечном
порядке. Число клеток то же, что и сейчас (170 759), так что стартап не дорожает.

Каждая клетка и каждый заголовок получают классы:

- `m0`, `m1`, `m2` — дорожка метрики (в порядке `data.metrics`);
- `g` — клетка принадлежит группе (итог или файл). Сегодня этот класс ставится только
  первой клетке группы (`appCell(cell, mi === 0, …)`); дальше он ставится **всем**
  клеткам группы, а какую из них рисовать границей — решает CSS (§2.3);
- класс `off` — клетка скрыта (ставится и снимается из JS).

Плюс одно правило в CSS:

```css
#grid .off { display: none; }
```

`border-collapse: collapse` уже есть (`table.css:3`), поэтому скрытие клеток
пересобирает ширину колонок корректно.

### 2.3. Левая граница групп — без единой строчки JS

Сейчас правило `.g { border-left: … }` (`table.css:11`) рисует границу у первой клетки
группы, и при выключенной метрике границу пришлось бы переставлять кодом. Вместо этого
её несёт первая *включённая* метрика — три правила вместо восьми комбинаций:

```css
#grid .g                          { border-left: 0; }
#grid:not(.m-off-0) .g.m0         { border-left: 1px solid rgba(127,127,127,.35); }
#grid.m-off-0:not(.m-off-1) .g.m1 { border-left: 1px solid rgba(127,127,127,.35); }
#grid.m-off-0.m-off-1 .g.m2       { border-left: 1px solid rgba(127,127,127,.35); }

#grid.m-off-0 .m0, #grid.m-off-1 .m1, #grid.m-off-2 .m2 { display: none; }
```

Правила действуют одинаково на группу итога и на группы всех файлов, поэтому граница
«итог | первый видимый файл» тоже переезжает сама — отдельного кода не нужно. Классы
`m-off-N` ставит на `#grid` обработчик метрики (§2.6). Все шесть правил вместе — 335
байт в артефакте.

### 2.4. Кэш ссылок на клетки — условие, без которого приём не работает

Это самая важшая деталь этапа. Замер `tools/perf/micro-dom.mjs`:

| Приём | Переключение одной колонки (642 клетки) |
|---|---:|
| Каждый раз читать `tr.children[i]` | 70,5 мс |
| Заранее собранные ссылки | **6,2 мс** |

Стоимость одной операции в jsdom: `classList.toggle` 0,0070 мс, `textContent`
0,0126 мс, **чтение `tr.children[i]` 0,0254 мс**, `group()` 0,0010 мс. То есть наивная
реализация тратит три четверти времени на доступ к детям строки, а не на переключение.

Кэш собирается бесплатно: при первом построении таблицы каждая клетка и так создаётся,
ссылку достаточно положить в массив. Обход уже готового DOM в прототипе стоил 2 924 мс
— это цена прототипа, а не решения.

Что кладём в кэш на каждую колонку файла `i` — **646 узлов**:

| Что | Сколько |
|---|---:|
| Клетки тела: 214 строк × 3 метрики | 642 |
| `th` группы в первой строке шапки (тот, что с `colSpan`) | 1 |
| `th` метрик во второй строке шапки | 3 |

Плюс отдельно:

- `totalCells[строка][метрика]` — 214 × 3 итоговых клеток (их не прячем, а перезаписываем);
- `spanTh` — 264 `th` с `colSpan` (оно у итога и у каждого файла);
- `rowsData[строка]` — номер строки данных; для строки «сейчас» — `null`.

### 2.5. Итоги инкрементально

Итог линеен: дельта суммы равна сумме дельт включённых. Значит при переключении файла
`i` достаточно пройти по строкам, где у файла было значение, и поправить накопитель:

```js
// totals[m][r] живёт в памяти и переживает клики
const v = data.rows[r].values[i];
if (v !== null) {
  totals[m][r] += on ? v[metricKey] : -v[metricKey];
  totalCells[r][m].textContent = group(Math.round(totals[m][r]));
}
```

Стоимость переключения файла — O(строк × метрик) вместо O(строк × файлов × метрик);
для папки из K файлов — O(строк × K × метрик).

Строка «сейчас» обновляется тем же накопителем: `now` равен `values` последней строки
(§1.2), поэтому её итог — это `totals[m][последняя строка]`. Отдельного пересчёта не
нужно, но забывать про эту строку нельзя: в прототипе она осталась необновлённой, и это
единственное расхождение прототипа с полным решением.

Тексты и дельты клеток файлов готовятся один раз при загрузке: уникальных значений
1 169, а форматирование всех непустых клеток стоит 63,6 мс — один раз вместо тех же
63,6 мс на каждый клик.

### 2.6. Обработчики кликов

**Файл.** Изменить `appView.files[i]` → для 646 узлов колонки
`classList.toggle('off', !on)` → поправить итоги (§2.5) → обновить состояния чекбоксов
(§2.7).

**Папка.** `folderFiles[path]` — готовый массив индексов → то же, что файл, по каждому
индексу → обновить чекбокс папки, всех её предков и категорию.

**Категория.** `filesByCategory[key]` — то же, по каждому индексу → обновить все
папки, в которых эти файлы лежат, и сам чекбокс категории.

**Метрика.** Один класс на корне таблицы и `colSpan` у шапки:

```js
grid.classList.toggle('m-off-' + mi, !on);
for (const th of spanTh) th.colSpan = visibleMetrics;   // 264 записи
appState(visibleMetrics, visibleFiles);                  // пустые состояния, §2.8
```

Замер того, почему именно так (`tools/perf/proto-hide.mjs`):

| Приём | Выключить | Включить | Операций |
|---|---:|---:|---:|
| Класс на `#grid` + `colSpan` | 2,20 мс | 1,37 мс | 265 |
| Перебор клеток метрики | 433,15 мс | 438,53 мс | 56 496 |

**Сворачивание папки** остаётся как есть: оно уже не вызывает рендер.

### 2.7. Панель на месте

Структура панели статична: 306 чекбоксов не меняются между рендерами, меняются только
`checked` и `indeterminate`. Панель строится один раз, а при клике правятся состояния.

Индексы, которые считаются один раз при загрузке:

```js
filesByCategory[key]  // индексы файлов категории
folderFiles[path]     // индексы файлов поддерева
folderParents[path]   // пути папок-предков
fileFolders[i]        // пути папок, в которых лежит файл i
```

Сейчас вместо этого `appIndexes` (`panel.js:28`) обходит каждое поддерево дважды — в
`panel.js:133` и в `panel.js:52`.

Обновление состояний:

- клик по файлу → его `input.checked`, затем для каждой папки из `fileFolders[i]` и для
  категории файла пересчитать `checked`/`indeterminate` по их спискам индексов;
- клик по папке → все файлы из `folderFiles[path]`, затем предки из `folderParents[path]`
  и затронутые категории;
- клик по категории → все её файлы, затем все папки, в которых они лежат.

Заодно исчезают два обходных механизма: `appScrollTop`/`appScrollBack` (`app.js:39–51`)
и возврат фокуса по порядковому номеру (`app.js:59–63`). Прокрутка больше не
сбрасывается, а узел с фокусом не уничтожается — сохранять нечего.

### 2.8. Пустые состояния и запись выбора

Пустые состояния уже устроены правильно и переносятся как есть: `appState`
(`table.js:73`) прячет `#shell` при нуле метрик и показывает `#state` с пояснением при
нуле файлов. Вызывать её из нового пути обновления вместо раннего `return` в `appTable`.

Запись выбора (`appWrite`) сейчас стоит 4,0 мс на клик. После этого этапа весь клик —
десятки миллисекунд, поэтому 4 мс становятся заметной долей:

- `appPassport()` закэшировать — это константа отчёта (FNV-1a по имени, схеме, пути
  артефакта, заголовку и 263 меткам);
- `history.replaceState` отправить в дебаунс на 150–300 мс, запись в `localStorage`
  оставить мгновенной.

## 3. Этап 2. Формат данных: разреженная история файла

### 3.1. Модель

Вместо снимка на каждый коммит — история каждого файла: записи только там, где размер
действительно изменился. На этом артефакте таких записей 1 169 против 56 019 клеток.

```js
{
  v: 2,
  tool:   [name, version],
  report: [locale, title, artifact, fixCommand, showSha],   // без heading и journal
  hrefPrefix: "https://github.com/…/commit/",
  metrics: [[key, label↓, note↓, method↓], …],              // ↓ — индекс в strs
  cats:    [[key, label↓], …],
  files:   [[label↓, path↓, [path↓…], catIdx, categoryBy, hist], …],
  rows:    [[sha↓, when↓, subject↓, section?], …],           // без values
  catalog: [[fileIdx | -1, path↓, why↓?], …],
  last:    [i, …],                                          // индексы, а не 263 буля
  strs:    [ … ]                                            // словарь строк
}

// hist — записи истории файла, каждая начинается с номера строки:
[ [row, raw, min, tok] ]        // появление файла: значения абсолютные
[ [row, dRaw, dMin, dTok] ]     // изменение: приращение к предыдущей записи
[ [row, 0] ]                    // файл исчез
```

Что куда девается из текущей модели:

| Сейчас | Становится |
|---|---|
| `rows[].values` — снимок на каждый коммит | `files[].hist` — только изменения |
| `now` | исчезает: восстанавливается из последней строки (§1.2) |
| `href` = префикс + sha | `hrefPrefix` один раз, sha берётся из `rows` |
| `last` — 263 буля | список индексов |
| `catalog[].path` | индекс колонки там, где путь совпадает (263 из 276) |
| `label`, `path`, подписи, пути — повторяются | ссылки в словарь `strs` |
| `report.heading`, `report.journal` | не передаются (§1.2) |

### 3.2. Кодирование

Порядок обхода детерминирован: файлы в порядке колонок, строки в порядке истории,
словарь пополняется по первому появлению. Это важно: артефакт пересобирается хуком
после каждого коммита (`.githooks/post-commit`) и обязан быть побайтово тем же на
любой машине.

### 3.3. Развёртывание на странице

`state.js` после `JSON.parse` разворачивает историю обратно в плотные снимки — за
O(числа изменений), а дальше вся страница работает в прежней модели. Расчёт
(`rowModel`, `totalsOf`, `cellParts`, `valueParts`) остаётся единственным местом, где
считаются числа: два способа считать одну строку — это два ответа.

Развёртывание удобно сразу класть в типизированные массивы — это то, что читает
инкрементальный итог из этапа 1:

```js
values[m] = new Int32Array(rows * files)   // 0 там, где файла нет
exists    = new Uint8Array(rows * files)
offset    = r * files + i
```

В куче при этом 1 169 объектов вместо 30 856.

### 3.4. Проверено

Кодировщик и обратное развёртывание написаны и прогнаны на этом артефакте
(`tools/perf/proto-payload-v3.mjs`): результат побайтово равен исходным `tool`,
`report`, `metrics`, `categories`, `files`, метаданным строк, всем 56 019 клеткам
`values`, `now`, `last` и `catalog`.

| Замер | Значение |
|---|---:|
| Блок данных сейчас | 1 361,8 КиБ |
| Блок данных после перехода, `method` сохранён | **81,5 КиБ** |

### 3.5. Две детали, которые легко потерять

- **`method` нужен и без признака точности.** Его печатает панель вне связи с
  точностью — `panel.js:187`: «raw — способ счёта: размер объекта git». Выбросить
  вместе с `accuracy` — значит потерять этот текст; с сохранённым `method` блок данных
  83 490 байт вместо 83 208.
- **Формат `--json`/`--data` можно не трогать.** Он запарирован с эталоном
  (`fixtures/parity`, `tools/parity-freeze.js`), а payload страницы собирается отдельно
  — `pagePayload()` в `src/page/build.js:101` со своим списком исключений `NOT_IN_FILE`.
  Поднимается `schema: 2`.

Старые записи выбора в `localStorage` и старые ссылки станут «чужими» — паспорт записи
включает `schema`, а страницу уже умеет их вежливо отклонять (`appRecordOk`,
`src/page/state.js:93`).

## 4. Этап 3. Вес артефакта

### 4.1. Комментарии

Замер `tools/perf/asset-weight.mjs`:

| Приём | JS | CSS | Вместе |
|---|---:|---:|---:|
| Сейчас | 49,6 КиБ | 18,8 КиБ | 68,4 КиБ |

| Минификация esbuild | 13,5 КиБ | 4,7 КиБ | **18,2 КиБ** |

Удаление комментариев даёт **42,9 КиБ из 50,1 КиБ** достижимой экономии — 86 % эффекта
без единой новой зависимости и без изменения поведения. Исходники остаются читаемыми и
проверяются линтером как сейчас: сжимается только артефакт, который сборщик и так
перекраивает при вклейке.

Порядок вклейки: `stripModules` снимает модульный синтаксис построчно, поэтому сначала
склейка глав и снятие модулей, потом сжатие, потом вставка в HTML.

### 4.2. Минификация и её условие

Минификация не меняет расчёт — проверено: `derived.js` 5 127 → 1 353 байт, `rowModel`
даёт побайтово равный результат по всем 213 строкам (168 057 клеток), `group(1234567)`
и `cellParts(5, -3)` совпадают.

Но esbuild лежит в `optionalDependencies`, и его отсутствие меняет числа
(`src/optional.js`: отсутствие — не отказ, а другой счёт). Если сборка артефакта станет
от него зависеть, машина без esbuild соберёт **другой файл** — сломается неподвижная
точка, ради которой отчёт пересобирается хуком после каждого коммита. Поэтому:

- удаление комментариев — своим кодом, детерминированно (42,9 КиБ);
- минификация — либо с закреплённой версией и отказом собрать отчёт без неё, либо не
  брать вовсе. Дополнительные 7,3 КиБ того не стоят, если цена — недетерминированность.

### 4.3. Сжатие блока данных

gzip уровня 9 на текущем блоке данных даёт 49,6 КиБ, в base64 — 66,2 КиБ. То есть
**−90 % размера доступно и без смены модели** — нужно только встроить сжатый блок и
распаковать его при загрузке.

У этого есть цена, и она не в размере:

- распаковка `DecompressionStream('gzip')` асинхронная, значит загрузка страницы
  перестаёт быть синхронной — первый рендер ждёт промиса;
- блок данных перестаёт быть читаемым: посмотреть его глазами или diff'ом уже нельзя.

Самодостаточность файла при этом сохраняется: распаковка идёт в браузере, сети не нужно.

## 5. Этап 4. Масштаб: виртуализация строк

213 строк — не проблема; тысячи строк — проблема: полная таблица растёт как
строки × файлы × метрики. В DOM держатся только видимые ~30–40 строк плюс распорки
сверху и снизу, задающие высоту.

- клетки: 170 759 → ~25 000, стартап и раскладка пропорционально дешевле;
- точечные правки на клик — только по видимым строкам;
- стартап перестаёт зависеть от длины истории.

Совместима с этапом 1 (видимость колонок не зависит от оконной логики) и с этапом 2
(окно по разреженной истории берётся по индексу строки, плотные снимки не нужны).

Что усложняется: оконная логика и синхронизация прокрутки, липкая первая колонка
(`.c-commit`, `table.css:15`) и липкая двухстрочная шапка (`table.css:7–9`), доступность,
поиск по странице, печать, копирование таблицы.

Дешёвая проба перед этим — `content-visibility: auto` на строках, но для таблиц он
требует `table-layout: fixed` с назначенными ширинами колонок.

Брать этап 4 имеет смысл, когда появятся отчёты на 1000+ строк: после этапов 1–3 клик по
метрике стоит 2 мс, а по категории из 105 файлов — 1,3 с в jsdom и, судя по цене одной
точечной правки, десятки-сотни миллисекунд в Chrome.

## 6. Удаление признака точности

Разделение значений на точные и приблизительные выпиливается. Что это убирает:

- **56 310 байт** данных (`approx`) и 127 байт словаря `#ui` — ключи `exact`,
  `approximate`, `approxCell` из 2 330 байт и 22 ключей. `methodLabel` остаётся: он
  подписывает способ счёта метрики, а не её точность;
- из `metrics[]` уходит поле `accuracy` (его читает только `panel.js:176`), поле
  `method` остаётся (`panel.js:187`);
- правило `#grid td.approx` (`app.css:119`) и класс `approx` в `appCellClass`
  (`table.js:22`);
- **336 000 посимвольных `charAt` за рендер**: `appApprox` (`table.js:9`) для каждой
  итоговой клетки проходит по всем включённым файлам (3 × 263) и для каждой клетки
  файла читает один символ (263 × 3) — 1 578 чтений на строку × 213 строк;
- из разреженной модели исчезает флаг точности в записи истории: −3,1 КиБ.

Правка сквозная: `approx`/`accuracy` встречаются в 16 файлах исходников —
`metrics.js` (23), `page/table.js` (14), `data.js` (6), `history.js` (4),
`page/state.js` (4), `locales.js` (4), `doctor.js` (3), `modes.js` (3), `tokens.js` (3),
`page/build.js` (2), `check.js`, `init.js`, `minify.js`, `project.js`, `strip.js`,
`page/panel.js` (по одному) — и в шести файлах тестов.

Делать это первым выгодно: уменьшается и блок данных, и число операций в рендере, и
объём всего остального.

## 8. Рассмотрено и отклонено

| Приём | Почему не берём |
|---|---|
| `DocumentFragment` при сборке строк | Уже фактически есть: строки строятся в отсоединённом `tbody` (`table.js:129`), который присоединяется одним вызовом (`app.js:26`) |
| Замена `forEach` на `for` в горячих циклах | Математика — 2 % клика, экономить нечего |
| Колонночная модель как способ **сжать файл** | В JSON не компактнее разреженной модели (81,5 КиБ уже получены). Как представление в памяти после развёртывания — берётся (§3.3), но это уже не про вес |
| Varint и собственный бинарный формат | Потеря читаемости ради КиБ, которые даёт обычный gzip |
| Готовая HTML-таблица в файле | Разметка в разы тяжелее данных, а итоги без значений файлов не пересчитать |
| Web Worker для расчётов | Страница открывается с `file://`, где создание Worker в Chrome исторически блокируется; после этапа 1 считать на клик почти нечего |
| Колонки-контейнеры вместо `<table>` (CSS grid) | Теряется семантика таблицы и доступность, переписывается вклеиваемый дословно `table.css`. Запасной путь, если виртуализации окажется мало |
| Общие префиксы путей | Словарь строк уже убирает повторение путей, а префиксы усложняют дерево |
| Упаковка `approx` в битовую карту | Признак точности выпиливается |
| Ленивый кэш дельт | При «строим один раз» дельты нужны сразу и один раз; лень добавит ветвлений без выгоды |
| Отдача `.html.gz` / `.html.br` | Не уменьшает файл на диске, а страница открывается двойным щелчком. Сжатие имеет смысл только встроенное (§4.3) |

## 9. Что не проверено

- **Все числа про Chrome.** Замеры здесь — jsdom 26 на Node 22.22.3. jsdom медленнее
  браузера в создании узлов и в правке классов, поэтому абсолютные миллисекунды в
  Chrome будут меньше; отношение «пересборка против точечной правки» сохраняется,
  потому что число операций то же.
- **Стоимость прохода раскладки** после точечной правки: прототип мерил только JS.
  Правка классов на 642 клетках вызовет пересчёт стиля — это «пол» подхода, и убирается
  он только уменьшением числа узлов (этап 4).
- **`visibility: collapse` на `<col>`** как способ спрятать колонку одной операцией
  вместо 642: в браузерах ведёт себя по-разному, нужен живой эксперимент. Запасной путь
  — класс на клетках, он и замерен.
- **`innerHTML` против `createElement`** при стартовом построении. В jsdom парсер
  медленнее, в браузере обычно наоборот; после этапа 1 полный рендер происходит один
  раз, поэтому выбор влияет только на стартап — решать замером в браузере.
- **Липкая шапка и липкая колонка коммита при скрытых клетках.** Скрытые клетки и
  пересборка ширинок — поведение стандартное, но `thead th` с `top: 0`/`top: 22px`
  (`table.css:7–9`) и `.c-commit` с `left: 0` (`table.css:15`) стоит посмотреть в
  браузере на живой таблице.
- **Web Worker с `file://`** — см. §8, в браузере не проверялось.
- Скрипты замеров написаны для этого разбора и не прогонялись через гейты репозитория
  (сенсоры раздувания, покрытия, `check:standards`).
